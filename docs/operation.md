# 運用の設計

desk のツリーを、人と AI エージェントが壊さずに使い続けるための設計。スキル `desk`・CLI `desk`・git がそれぞれ何を受け持ち、ずれや衝突をどう扱うかを書く。ツリーの形と書き方は [tree.md](tree.md)、CLI のコマンドは [cli.md](cli.md)。

## 1. 役割分担

| もの | 役割 |
| --- | --- |
| 仕組みのリポジトリ | CLI のコード（`cli/`）、スキルの本体（`skill/`）、設計文書（`docs/`）。ドキュメントのツリーとは分ける |
| スキル `desk` | **決まりの正本（形・書き方・手順の全部）で、必須。** 始めに何を読み、どう確かめ、どう書き、どう直し、終わりに何をするか。本体は `skill/SKILL.md`。エージェントのスキルの場所からリンクして使う（4 節） |
| CLI `desk` | スキルと同じ形を実装した補助ツール。形どおりに作る `init`・`new`、形で引く `ls`・`graph`、必要な深さだけ読む `read`、形に合っているか確かめる `check`、リンクを付け替えながら動かす `archive`・`mv`（cli.md） |
| README.md（ルート・プロジェクト） | 軽い概要。何のツリー／プロジェクトか、どこに何があるか、人が書くときの決まり 3 行、詳しくはどこか。決まりの正本ではない。ルートのものは `desk init` が、プロジェクトのものは `desk new project` が作る |
| git | 履歴と、戻す手段。壊れたときの「何がいつ変わったか」はここで分かる。CLI はコミットしない |
| エージェント | 中身を書く。何を読むか決める。外の世界（コードリポジトリ・PR）と突き合わせる。コミットする |
| 人 | エディタで直接書く。形を守らなくてよく、コミットもしなくてよい。CLI は使わない |

## 2. 前提

- **正本はファイルと git。** 人もエージェントも直接読み書きする。エージェントの memory の機能は使わないので、ツリーが読まれる入口はスキルだけ
- **CLI は「形」を扱い、エージェントは「中身」を扱う。** 形とは、ディレクトリ、ファイルの名前と節、frontmatter、相対パスのリンク。形どおりに作る・形で引く・必要な深さだけ読む・形に合っているか確かめる・形を保って動かす、は CLI。何を書くか・何を読むか決める・外の世界と突き合わせる・コミットする、は CLI にせず、スキルに手順を書く
- **CLI は補助ツールで、無くても成り立つ。** CLI を通さないと書けない・コミットできない、という強制はしない。ロック・印・hook も持たない
- **決まりの正本はスキルで、スキルは必須。** CLI は同じ形を実装する。「1 つの事実は 1 か所」はツリーの中身の決まりで、スキル・CLI・設計文書には当てはめない
- **ワーキングツリーは 1 本で、全セッションが `main` に直接コミットする。** ブランチや worktree を分けると、他のセッションの変更が見えない間に古い理解で書き、マージで行は通るのに中身がずれる
- **ずれは手順ではなく基準で扱う。** セッションの始めや月 1 度のような定期の点検は無い。ずれには 2 種類あり、混ぜない。放置されて形骸化した反映漏れ（PR が閉じているのに `inprogress`、など）は 3.1 の基準で、直近の作業がぶつかって起きた不整合は 3.3 の基準で直す
- **同時書き込みは厳密に防がず、後から直せれば十分。** 壊れにくい書き方と、壊れたときの見つけ方と直し方を持つ（3.3）
- **人も直接書く。** 人とエージェントがぶつかる場面を別に考える（3.4）
- **守りたいのは内容の不整合で、放置ではない。** 触られていないファイルは、中身が正しければそのままでよい

起こりうる問題と、この文書のどこで扱うか:

| 問題 | 対策 |
| --- | --- |
| 作業は進んでいるのに文書が古い。アーカイブされずに残る | 進めた側がそのとき書く。見つけたずれは直すべきもので、しきい値を待たない（3.1） |
| 元になるものが変わったのに、それを書いている文書が直されない | 変化の起点があるものだけ直す。古いだけのものは挙げない（3.2） |
| 複数のエージェントが同時に書き込んで壊れる・ずれる | 壊れにくい書き方 3 つ、気づく場所 2 つ、直すのは誰かを決める基準 3 つ（3.3） |
| 人とエージェントの作業がぶつかる | 人の書き方を縛らず、エージェント側が人の変更を読む・混ぜない・消さない（3.4） |
| ナレッジを段階的に読まない（全部 `cat` してしまう） | 概要だけ・本文・詳細までを切り出す `desk read`（と `ls`・`graph` の `--level`）。どの段まで読むかはスキルの手順（3.5） |
| ディレクトリ・frontmatter・節の形が崩れる | `desk new` が形どおりに作り、`desk check` が形を確かめ、機械的な直しは `--fix` でやる（cli.md） |
| 決まりがどこにあるか分からない | 正本はスキルで必須。CLI は同じ形を実装し、README は概要（1 節） |

## 3. ずれの守り方

### 3.1 進んでいるのに書かれていない

反映漏れと、放置されて形骸化した不整合（アーカイブ漏れを含む）の話。文書の `status` や日付を信じず、**進み具合が分かる別のもの（コードリポジトリや PR など）と突き合わせる。** 基準は 2 つで、しきい値や定期の点検は無い。

- **進めた側が、そのとき書く。** 作業を進めたセッションが、同じ区切りでタスクのファイルを直す
- **見つけたずれは直すべきもの。** 「N 日たってから」のようなしきい値は持たず、セッションの始めの定期確認にもしない。今のタスクにかかわるずれ（自分のタスクの文書のずれと、今のタスクの変更が生んだずれ）は、どのファイルにあっても、直すかどうかを自分で決める。使い捨ての `artifacts/` は、直す価値が無ければ放っておいてよい。今のタスクと関係ない場所で見つけたずれは、黙って直しも放っておきもせず、ユーザーに伝えて確認が取れたら直す。責務から外れて本題が進まなくなるのを避けるため。その直しが他の作業とぶつかったら 3.3 の基準で直す

ツリーの中だけで分かるずれは `desk check` が挙げ、外の世界との突き合わせはエージェントがやる。タスクの `archive/` への移動は `status` から決まるので、`desk archive` はいつやっても同じ。

- 触られていないだけのタスク（コードにも PR にも動きがない）はずれではない
- 人に聞くことなら、`needs_human: true` の子タスクにする

### 3.2 元が変わったのに直されていない

「いまこうなっている」を書いている文書（`wiki/`、ナレッジ、原則）は、元になるものが変わったら直す。**古いだけでは挙げず、変化の起点があるものだけ挙げる。** 定期的な点検は要らない。確かめて変えなかったときは `verified` に日付を書いてよい（任意）。

### 3.3 同時に書いたとき

複数のセッションが同じツリーを書く。**厳密には防がない。** 壊れにくい書き方を 3 つ守り、壊れたら見つけて直す。git に小さく残っていれば、何がいつ変わったかは追えるので直せる。

**壊れにくい書き方（習慣であって保証ではない）。**

1. **既存のファイルは全体を書き直さず、直前に読み直して、該当箇所の置換で直す。** 置換元が変わっていれば失敗して、古い理解で上書きしたことに気づける。追記（タスクのログ・素材）は末尾だけ
2. **`git add <パス>...` だけ使い、小さくこまめにコミットする。** `git add -A` を使わない。これで他のセッションや人の途中の変更を巻き込まない
3. **1 つのタスクのファイルを同時に書くのは 1 つのセッションだけ。** 並べて進める作業は子タスクに分ける。ずれを直すために他のタスクのファイルを書くときは、要る箇所だけを 1 の書き方で直す。誰がどのタスクを持つかはツリーに書かない

**壊れ方と直し方。** 4 通りある。git のブランチや worktree を分けても防げるのは 1〜3 までで、4 は構造と確かめでしか扱えない。

1. **1 ファイルの破壊。** 2 つのセッションが同じファイルを読んで書き、後の書き込みが前の変更を消す。`git diff` に「自分が書いていないのに消えた行」があるか、置換が失敗して気づく。`git log -p <ファイル>` で消えた変更を見て戻す。置換で書いていれば起きにくい
2. **git の操作。** `git add -A` が途中の変更を巻き込む。同時の `commit`。コミットに自分のタスク以外のファイルが入っていて気づく。`git reset HEAD~ --soft` で分け直す。習慣 2 で起きにくい
3. **テキストの衝突。** ブランチを分けた場合のマージ衝突。1 本のワーキングツリーなので起きない
4. **内容の不整合（テキストは衝突しない）。** archive に移した後に古いパスへ追記して同じ名前のファイルが 2 つになる。相手が動かしたファイルへの古いパスのリンクを書く。`wiki/` の値を直した直後に古い値を前提の文書を書く。「いま」を古い理解で書き直す。同じ日に同じ slug で作る。書く直前の読み直しと、コミット直後の `git log`（下の「気づく場所」）で気づく。手元で確かめたければ `desk check`。重複したファイルは中身を 1 つに寄せて片方を消し、古い値を前提にした文書は読み直して書き直す

ツリーの構造（tree.md の決まりそのもの）が、4 の面積を減らしている。1 つの事実は 1 か所、状態はタスクのファイルの 1 節にだけ、記録は追記だけ、識別はパスで名前は種類の中で一意、導出できるものは書かない。これがあるので、4 が起きても直す場所は 1 つで済む。

**気づく場所は 2 つ。**

- **書く直前。** 読み直して置換で書く（習慣 1）。同じ箇所を相手が先に書いていれば置換が失敗し、別の箇所なら読み直したときに相手の変更が目に入る
- **コミットした直後。** `git log --since=<セッションの始め> --format='%h %s' -- <自分が触ったファイル>` を見る。自分のタスク以外のコミットが混ざっていたら、その差分を読んで自分の変更とずれていないか見る。あわせて `git show --stat HEAD` で、自分のコミットに自分が書いていない変更（相手の途中の変更）が入っていないか見る

機械で見つかるのは構造のずれまで。「いま」を古い理解で書き直した、`wiki/` の値と別の文書の前提がずれた、といった意味のずれは、次にそれを読むエージェントが気づく。だから 1 つの事実は 1 か所にして、読む場所と直す場所を 1 つにしている。

**直すのは誰かの基準は 3 つ。** 手順を増やさず、これで判断する。

1. **不整合を含むコミットを入れた側が直す。** 順番ではなく、どのコミットに入ったかで決まる。たいていは後からコミットした側（コミット直後の確認で相手のコミットが見えるのはその側）。ただし 1 本のワーキングツリーでは、先に `git add <パス>` した側が相手の途中の変更まで同じコミットに入れてしまうことがあり（後の側はコミットするものが無いか失敗する）、そのときは先にコミットした側。どちらでも直す責任は 1 つに決まる
2. **直すのは自分の側だけ。** 相手が書いた中身は触らない。相手の側にも直しが要るなら、相手が自分で直す（3）。ユーザーには確認しない
3. **相手側にも直しが要るなら、相手自身が、こちらの直しが済んでから対応する。** こちらは自分の直しを先にコミットして待つだけ。相手は次に書くかコミットしたとき（気づく場所と同じ）にこちらの直しを見て、自分の側を直す

### 3.4 人が直接書いたとき

人はエディタで直接書く。形を守らなくてよく、コミットもしなくてよい。**合わせるのはエージェント側。** 人が書くときの決まりは README に 3 行だけ: どこに書いてもよい、迷ったら `inbox/`、コミットはしなくてよい。

場面ごとのエージェントの決まり:

- **人がファイルを書いて、コミットしていない。** 作業ツリーが HEAD より新しい。読むのは作業ツリー（いつもどおり）で、人の未コミットの変更はそのまま正として読む。人の変更は人のもので、自分の変更と混ぜない（習慣 2）。セッションの終わりに人の変更が残っていれば、別のコミット（`docs(<タスク>): 人の編集を取り込む`）で入れる
- **人がエディタで開いているファイルを、エージェントが置換で直す。** エディタは、変更されていないバッファなら読み直し、変更中のバッファなら保存時に上書きの確認が出る。人が最近触ったファイル（`git status` で未コミット、か直近のコミットが人の編集の取り込み）は、できるだけ書かない。書いたら「いま」か報告で伝える
- **人が保存して、エージェントの変更を消す。** エディタは全体を書くので、古いバッファの保存はエージェントの直近の変更を消す。エージェントは書いたらすぐコミットしておく（習慣 2）。そのファイルに書く前の読み直しで `git diff -- <ファイル>` を見て、**人の未コミットの変更に、直近のコミットで足した内容の削除が含まれていたら、意図した削除か人に聞く**（`needs_human: true` の子タスクか、直接）
- **人が形を守らずに書く。** frontmatter が無い、名前に日付が無い、リンクが絶対パスや `~` 始まり、ファイルを Finder で動かしてリンクが切れた、など。`desk ls` や `desk graph` から漏れ、`desk check` が挙げる。見つけたエージェントが整える。足りない frontmatter のキーは `desk check --fix` が空で足し、値は手で書く。切れたリンクは、同じ名前のファイルがツリーに 1 つだけあれば `--fix` が付け替え、それ以外と名前は手で直す。文面は人の言葉を書き換えない（`inbox/` と同じ）

### 3.5 段階的に読む

tree.md 6 節の段 0・1・2 を、名前だけで、必要な深さだけ読める形にする。**切り出しは CLI、何をどの段まで読むかはスキル。**

素の操作だと「概要だけ」が切り出しにくい。`description` は複数行の YAML でもよく `grep '^description:'` では切れる、`head` は節の途中で切れる、「いま」の 1 行目や特定の節だけを取るには毎回 awk を書く。だからエージェントは結局 `cat` で全部読んでしまう。ここは CLI に持たせる。

- 段 0（ルートと作業中のプロジェクトの、原則の本文と、全ナレッジの名前と `description`）: `desk ls principle --project <p> --level 1`、`desk ls knowledge --project <p> --level 0`
- 段 1（ナレッジの本文）: `desk read <パス>`
- 段 2（本文が指す詳細）: `desk read <パス> --level 2`
- 長い文書: `desk read <パス> --outline` で見出しだけ、`desk read <パス> --section <見出し>,...` で要る節だけ

どの段をいつ読むかは tree.md 6 節とスキル 6 節にあり、ここでは繰り返さない。

- 段 0 の出力は 1 件 1〜3 行（名前、種類、`description`。タスクなら `status` と「いま」の 1 行目も）。ナレッジが 100 件あっても、始めに読むのは数百行で済む
- `desk graph <パス>` は隣接（指す原則、詳細、根拠、指されているもの）を段 0 で出すので、次に何を読むかをそこで決める。読むと決めたら `desk read`
- スキルの決まり: 作業の種類が変わったら段 0 を見直して段 1 を読む。ナレッジに従わなかったときは理由をタスクのログに残す。ナレッジが古ければ直すか、`materials/` に 1 件書く
- CLI が無いときの代わりは `cat`（全部読む）と `grep -H '^description:'`（1 行の `description` だけ拾える）。読めなくはないが段 0 が成り立たないので、ここは CLI に持たせている

## 4. スキル `desk`

### 置き場所と読み手

- 本体は仕組みのリポジトリの `skill/SKILL.md`。エージェントのスキルの場所（Claude Code なら `~/.claude/skills/desk`）からシンボリックリンクで指し、スキルの変更も設計と同じリポジトリの履歴に残す
- 読むのは、ツリーに触るエージェント
- 決まりの正本はこのスキルで、ツリーに触るエージェントは必ず全部読む。形（種類ごとの置き場所、名前、frontmatter、必須の節）も書き方も手順もここに書く。CLI は同じ形を実装した補助で、あれば使い、無ければ素の操作でやる。README は概要なので、決まりの根拠にしない。決まりの理由はこの `docs/`

### 中身の構成

エージェントが上から読んでつまずかない順に並べる。形を知ってから、どこに何を書くかを知り、そのあと時間の流れに沿った手順、最後に守り方と早見。頭に番号なしの「このスキルについて」（ルートの見つけ方（ツリーの中で `desk root`）、正本はスキル、CLI は補助、README は概要、理由は `docs/`、書いていないケースは原則に戻る）があり、続く節の番号はスキルの節番号そのまま。

1. **原則。** tree.md 1 節と同じ 8 つ
2. **ツリーの形。** 全体、ファイルの名前、リンク、静的ファイル（tree.md 2 節）
3. **タスク。** タスクと手順、ファイルの形、ログ、人が要るタスク（tree.md 3 節）
4. **タスクの文書。** `artifacts/`（tree.md 4 節）
5. **タスクを離れて残るもの。** `wiki/`・`inbox/`・`library/`（tree.md 5 節）
6. **原則・ナレッジ・素材。** 3 層と、段階的な読み方（tree.md 6 節）。2〜6 節の形は `desk new` と `desk check` が同じものを実装し、README には書かない
7. **どの情報をどこに書くか。** tree.md 7 節と同じ。情報と場所の対応だけを並べ、時制は場所ごとの節にある
8. **アーカイブと移動。** tree.md 8 節
9. **セッションの流れ。** 始めに読むもの（プロジェクトの README → 原則の本文とナレッジの段 0 → タスクと親の頭 → `artifacts/` と関係する `wiki/` → 要るナレッジ。全部 `cat` しない）と、見るのは `git status` だけで定期の点検はしないこと。進めながら（進めた側がそのとき書く、人に聞くことは `needs_human: true` の子タスク、指摘はその場で素材に、作業の種類が変わったら段 0 を見直す、見つけたずれは直す）。タスクを閉じるとき（子が全部終わっているか → 一緒に移す文書を選んで `desk archive` → その変更だけを先にコミット）。終わりにやること（現在地と手順 → ログ → 「いま」と「成果物」 → 変わったことを書いている文書 → 棚卸しの提案 → 自分のファイルだけをコミット → 人の変更は別のコミット）
10. **同時に書いても壊さないために。** 3.3 の習慣 3 つ、気づく場所 2 つ、直すのは誰かの基準 3 つ。3.4 の人が直接書いたときの決まり。新しいファイルは `desk new` で作る
11. **書き方の決まり。** tree.md 10 節
12. **やらないこと。** `git add -A`、既存ファイルの全体の書き直し、一覧を手で書く、決まりをツリーの中に複製する、コードリポジトリに作業用の md を作る、人の未コミットの変更を混ぜる、人の言葉を書き換える、今のタスクと関係ない場所で見つけたずれをユーザーに伝えずに直す・放っておく、同時に書いてぶつかったときに相手が書いた中身を直す、原則とナレッジを確認なしに足す・変える
13. **CLI の早見。** コマンドと、よく使う形
