# ツリーの構成と書き方

desk は、あらゆるプロジェクトとタスクのドキュメントを、浅いディレクトリと markdown の frontmatter で 1 つのツリーに一元管理する仕組み。扱うのは、タスク（AI と人）と依存、調査、計画、作業の記録、レビュー、ブランチ・worktree・PR の構成、ナレッジとその素材、メモ、あとで参照したい情報の控え。

読み手はユーザー本人と AI エージェントだけで、他の人への引き継ぎ、個人とチームを分けるスコープ、git のリモートは考えない。ナレッジの正本はこのツリーで、エージェントの memory の機能は使わない（正本が 2 つになる）。

この文書は、ツリーの形と、何をどこにどう書くかの設計。スキルと CLI と git でツリーを壊さずに使い続ける設計は [operation.md](operation.md)、CLI のコマンドは [cli.md](cli.md)。エージェントが読む決まりの正本はスキル `desk`（`skill/SKILL.md`）で、この文書はその理由を書く。

## 1. 原則

細かい決まりは全部ここから導く。書いていないケースに出会ったら、ここに戻って判断する。

1. **プロジェクトはみな同じ形。ルートには全プロジェクトに適用するものだけを置く。** タスクとその文書は必ずどれかのプロジェクトにある。どのプロジェクトにも属さないもののために、なんでもありのプロジェクトを 1 つ置く
2. **ディレクトリは種類で分け、中はフラットに並べ、関係はリンクで表す。** 入れ子はプロジェクトの中で `<種類>/<ファイル>.md` の 2 段まで（例外は永続の文書 `wiki/` と、静的ファイルの `assets/` だけ）。親子・依存・「どのタスクの文書か」は、frontmatter と本文の相対パスのリンクで表す
3. **1 つの事実は 1 か所に書く。** 他の場所からはリンクで指す。どこに何を書くかは 7 節が正本。これはツリーの中身の決まりで、スキルや CLI などツール側には当てはめない
4. **人に読ませるものは、簡潔に分かりやすく書く。** README、タスクの目的・いま・成果物、成果物の文書は、結論から短く
5. **時制を混ぜない。** 状態（いまどうか。上書きする）、記録（何があったか。追記だけする）、知識（次も使えること。磨いて書き直す）の 3 つを、ここでは「時制」と呼ぶ。時制の違うものは別のファイルに書く。例外はタスクのファイルだけで、状態の節の下に記録の節（ログ）を 1 つ持つ
6. **ファイルは要るときに作り、中身のない節や文書は置かない。** 形はスキルに書いてあり、`desk new` が形どおりに作る。雛形のディレクトリは置かない
7. **工程を状態にしない。** 調査中・設計中・レビュー待ちのような工程は進め方で変わるので、状態の語彙にしない
8. **git と名前で分かることは書かない。** 作成日はファイル名に、変更の時系列と古い版は git にある

## 2. 全体の形

```
<ルート>/
├── .desk              # ルートの印
├── README.md          # 軽い概要（何のツリーか、どこに何があるか、人が書くときの決まり 3 行）
├── principles/        # 全プロジェクトに通じる原則（6 節）
├── knowledge/         # 全プロジェクトで AI が使う知識（6 節）
├── assets/            # README の画像など（要るときに）
├── archive/
│   └── projects/      # 終わったプロジェクト。中は projects/ と同じ形（8 節）
└── projects/
    ├── misc/          # どのプロジェクトにも属さないものを置く、なんでもありのプロジェクト
    └── <project>/     # 長く続く文脈（プロダクト・リポジトリ・領域）
        ├── README.md      # 何のプロジェクトか（概要）
        ├── tasks/         # タスク。1 タスク 1 ファイル（3 節）
        ├── artifacts/     # タスクの文書。タスクと一緒に役目を終える（4 節）
        │   └── assets/    # 画像などの静的ファイル
        ├── wiki/          # プロジェクトの成果物としてメンテする文書。構成はプロジェクトで設計する（5 節）
        ├── inbox/         # まだどこにも属さない未整理のものの受け箱。棚卸しして空にする（5 節）
        ├── library/       # あとで参照したい情報の控え。書いた時点のまま残す（5 節）
        ├── principles/    # このプロジェクトだけの原則（6 節）
        ├── knowledge/     # このプロジェクトだけで AI が使う知識（6 節）
        ├── materials/     # ナレッジの素材。1 件 1 ファイル（6 節）
        ├── assets/        # README の画像など（要るときに）
        └── archive/       # 終わったタスクのもの。中は上と同じ形（8 節）
```

### ルートとプロジェクト

- **ルートに置くのは決まった名前だけ。** `.desk`・`README.md`・`principles/`・`knowledge/`・`assets/`・`archive/`・`projects/`。ルートにあるのは概要と、全体の原則とナレッジで、タスクとその文書は置かない。プロジェクトは `projects/` にまとめ、ルートの中身とプロジェクトの名前が混ざらないようにする
- **ルートの印 `.desk`。** `.desk` のあるディレクトリがルート。CLI は作業ディレクトリから上にたどってこれを探す。ツリーの置き場所は、ツリーにも仕組みのリポジトリにも書かない
- **プロジェクトは長く続く文脈。** プロダクト・リポジトリ・領域。複数の PR にまたがる大きな作業はプロジェクトではなく、子を持つタスクにする。`projects/` の下に平らに並べ、入れ子にしない。プロジェクトの直下に置くファイルは README.md だけで、ディレクトリは中身があるものだけ置く。なんでもありのプロジェクト（`projects/misc/`）も形は同じ
- **雛形は置かない。** 形も決まりもスキルにあり、ツリーには置かない
- **`.` で始まる名前は形の外。** `.desk`・`.git`・`.gitignore`・`.DS_Store` など

### 名前・リンク・静的ファイル

- **どのディレクトリの中もフラット。** 例外は `wiki/` で、構成をプロジェクトごとに設計するので入れ子にしてよい
- **名前は `<slug>.md`。** タスク・素材・inbox・library は作った日を頭に付けて `YYYY-MM-DD-<slug>.md`。slug は英小文字・数字・ハイフンで、中身で付ける。識別はパスで、名前は同じ種類の中（そのプロジェクトの `archive/` の同じ種類も含めて）で一意にする
- **リンクは相対パス。** 本文は markdown のリンク `[文字](../artifacts/print-layout.md)`、frontmatter は同じ相対パスの文字列。基準はどちらもそのファイルの場所。絶対パス、`~` 始まり、名前だけのリンク（`[[名前]]`）は書かない。一般的なビューワーやエディタがそのまま開けることが目的。ファイルを動かしたら、動かしたファイルの中のリンクと、それを指しているリンクを付け替える（`desk archive`・`desk mv` がやる。8 節）。ログに書いた決定を指すときは、そのタスクのファイルへのパス（`../tasks/<タスク>.md`）で指す
- **画像などの静的ファイルは、それを指す文書と同じディレクトリの `assets/` に置く。** `artifacts/assets/`・`wiki/assets/`。README のものはプロジェクト直下やルートの `assets/`。中はフラット。文書からは `![](assets/print-sample.png)` で指す。どこからも指されていないものは `desk check` が挙げる。文書を `archive/` に移すときに一緒に移すなら、同じ `desk archive` にまとめて指定する

## 3. タスク

### タスクは必ずファイル

`tasks/<YYYY-MM-DD>-<slug>.md`。1 タスク 1 ファイル。小さくてもファイルを作り、複数のタスクをまとめて書くファイルは置かない。どのプロジェクトにも属さないタスクは、なんでもありのプロジェクト（`projects/misc/`）に置く。

タスクと手順の区別:

- **タスク**（ファイル）: 終わりの条件があって、ブランチ・PR・別のセッション・人への依頼のどれかを持つもの
- **手順**（タスクのファイルの中の行）: そのタスクの中で順にやるだけのこと。チェックボックスで書く。手順がタスクの条件を満たすようになったらファイルに切り出し、行を `→ [子の見出し](<子のファイル>.md)` に置き換える

### ファイルの形

```markdown
---
status: inprogress        # backlog / todo / inprogress / done / dropped
needs_human: false        # false / true
parent: 2026-09-07-meal-planner.md                           # 同じ tasks/ の中なのでファイル名だけ
depends_on: [2026-10-14-meal-planner-shopping-list.md]
repo: ~/src/recipe-app
branch: feature/meal-planner/printable-menu   # base: feature/meal-planner/all
worktree: ~/src/recipe-app-worktrees/meal-planner
pr: https://github.com/example/recipe-app/pull/128
---

# 献立を印刷できるようにする

## 目的
3 行まで。終わりの条件を含む。

## いま
人が知るべき粒度で 3 行まで。人にとって意味のある変化のときだけ書き換える。

## 成果物
- PR: #128, #129, recipe-api #42
- [印刷のレイアウト](../artifacts/print-layout.md)

## 現在地
次の一手と、何を待っているか。セッションごとに上書きする。

## 決まり
このタスクの中だけの運用（ブランチの切り方、確認のしかたなど）。

## 手順
- [x] 献立を印刷用の形に並べる
- → [印刷のプレビューを出す](2026-11-11-print-preview.md)
- → [用紙の大きさを決める](2026-11-10-decide-paper-size.md)
- [ ] レビューの指摘 1〜4 に返信する

## ログ
### 2026-11-10
- 決定: 印刷用のページは画面と別に作る。理由: 画面をそのまま印刷すると、ボタンやメニューまで出る
- 試してやめた: 画面に印刷用のスタイルを当てるだけにする。1 週間分が 1 枚に収まらなかった
```

**節。** 目的・いま・成果物は人が読むところで、結論から短く（原則 4）。現在地・決まり・手順は状態で、上書きする。いちばん下のログは記録。成果物の節は、PR と、成果物の文書へのリンク。数行で済む本当に軽い中身（確認の結果など）だけは、ファイルを作らずに直接書いてよい。

**frontmatter。**

- `status` と `needs_human` は必須
- `status` は `backlog`（やるか決めていない・いつか）、`todo`（やると決めた・未着手）、`inprogress`（着手している）、`done`、`dropped`。待っていることは `depends_on` で表す。工程は書かない（原則 7）
- `needs_human` は、人の判断か作業が要るかどうか。誰がやるかではない
- `parent`・`depends_on` は、タスクのファイルへの相対パス（同じ `tasks/` の中ならファイル名だけ）
- `repo`・`worktree` は `~` からのパス。このツリーはコードリポジトリと別の場所にあるので、相対パスにしない
- ブランチ・base・worktree・PR は、タスクが 1 本の枝を持つときに書く。複数の枝を持つなら、子タスクに分けるか、手順の行の末尾に書く。ブランチなどの正本はタスクのファイルだけで、ほかには書かない

**親子と依存。**

- 親子は、子の `parent` だけで表す。親のファイルに子を列挙しない。順序や依存を示したいときだけ、親の手順に `→ [子](<子のファイル>.md)` の行を置く（チェックボックスは付けず、状態は子だけが持つ）
- 依存は、待つ側（後のタスク）の `depends_on` にだけ書く。逆向きは検索で引く
- 親子（`parent` をたどってつながる祖先と子孫）の間には、どちらの向きにも依存を張らない。依存は「着手できるか」を表し、親子は抽象度が違うだけの包含関係だから。子の判断を待っている親も、途中まで進めているので `inprogress` のまま
- ほかの依存から導ける依存は書かない。祖先の依存は子孫にも効き、依存は推移し（A→B→C なら A→C）、依存先の子孫にも依存している（親が終わるのは子孫が全部終わったとき）ので、導けるものは書いても意味がない。子孫で書くのは、子孫どうしの依存と、特定の子だけが外の別のタスクを待つとき

### ログ

そのタスクの決定と経緯を、タスクのファイルのいちばん下の「ログ」の節に、日付の小見出しで追記だけする。節は要るときに作る。別のファイルにはせず、1 セッション 1 ファイルの作業ログも作らない。

- 書くのは、決定（`決定:` で始め、理由と却下した案を添える）と、残す価値のある出来事
- 書かないのは、やったことの羅列（git のコミットにある）、次の一手（現在地にある）、人に聞くこと（人が要るタスクにある）
- 決定を指すときは、それを書いたタスクのファイルへの相対パス（`../tasks/<タスクの名前>.md`）で指す。指すのはファイルまで
- 上の節は上書き、この節は追記だけ（原則 5 の例外）。同じファイルに置くのは、タスクが終われば一緒に役目を終え、別に引く場面が無いため。`desk read <タスク> --section 目的,いま,決まり` のように節で切れば、ログを読まずに済む
- 長くなってきたら、それはタスクが大きすぎる印なので、子タスクに分ける

### 人が要るタスク

人に判断してほしいこと（確認）も、人がやる作業も、**`needs_human: true` のタスクに切り出す。** 形は同じ。こうすると、確認の中身は人が要るタスクのファイルで、答えはその成果物で、全部タスクの仕組みに載る。つなぎ方は、そのときに合うものを選ぶ。

- 切り出した元のタスクの子にする。その続きの作業も子に分けて、人が要るタスクに `depends_on` を張ってもよい
- 親子にせず、待つ側の `depends_on` で指す

```markdown
---
status: todo
needs_human: true
parent: 2026-11-09-printable-menu.md
---

# 用紙の大きさを決める

## 目的
a A4 だけ / b A4 と B5 / c 使う人が選ぶ。おすすめ a（家庭のプリンターはほとんど A4）。

## 成果物
- 決定: [献立を印刷できるようにする](2026-11-09-printable-menu.md) のログ
```

- 節は 目的・成果物 の 2 つ。目的に、聞きたいことと選択肢とおすすめを書く
- 終わったら、決定や結果は切り出した元のタスクのログに書き、人が要るタスクの成果物からそれを指して `done` にする
- **人宛ての一覧**は、`needs_human: true` で動いているタスクを集めて出す（9 節）。手で保つ受け箱は置かない

## 4. タスクの文書（`artifacts/`）

タスクのための文書。設計、調査の結果、レビューの結果など。どれも使い捨てで、タスクが終われば `archive/` に移す。

```yaml
---
tasks: [../tasks/2026-11-09-printable-menu.md]
---
```

- 名前は中身で付ける。frontmatter の `tasks` で、どのタスクのための文書かを指す（複数でもよい。仕様を複数の PR で使うなど）
- 整理して書く。結論から書き、新しく分かったら最初からそうだったように書き直す（10 節）
- 成果物は、タスクの「成果物」から指す
- 画像や図は `artifacts/assets/` に置き、`![](assets/print-sample.png)` で指す（2 節）

## 5. タスクを離れて残るもの

タスクに属さず、タスクが終わっても残るものが 3 種類ある。違いは何をどう書くかにある。`wiki/` はメンテし続ける文書、`inbox/` は人の言葉をそのまま置く受け箱、`library/` は書いた時点のまま残す控え。

### 永続の文書（`wiki/`）

仕組みの説明、仕様、用語など、**プロジェクトの成果物としてメンテし続ける文書。** コードリポジトリの中の docs と同じ扱いで、プロジェクトごとに構成を設計して使う。タスクには属さない。置き場所に困ったものの受け皿ではない。タスクの文書（`artifacts/`）とは別のディレクトリに置くことで、ここにあるものは全部メンテの対象だと置き場所で言い切れる。

```yaml
---
description: 献立プランナーの仕組み全体。レシピ API との境目を触るときに読む   # 必須
verified: 2026-11-12        # 任意
---
```

- 構成はプロジェクトごとに設計する。入れ子にしてよい（フラットの唯一の例外）
- 特定のタスクの話は、そのタスクが終わっても残すもの（保守に要るなど）だけ置く。タスクに紐づく文書は、大きなタスクの進め方のようなものも、そのタスクの `artifacts/` に置く
- frontmatter の `description` に、何が書いてあるか・いつ読むかを書く。AI は `description` を集めて、関係するものだけ読む（ナレッジの段 0 と同じ）。確かめたが変えなかったときは `verified` にその日付を書いてよい（任意）
- メンテし続けられる量だけ持つ。古いだけの文書は問題にしない（中身が正しければそのままでよい）。メンテされなくなったら消す
- 最初からそうだったように書き直す（10 節）。経緯は書かない
- `archive/` には移さない。プロジェクトが終わるときにプロジェクトごと移る
- 近いものとの違い: `artifacts/` はタスクのための文書（使い捨て。大きなタスクの進め方も、そのタスクの文書）。`knowledge/` は AI が作業で使う決まり・手順・事実（短く、原則に紐づく。特定のタスクに限らない開発の流れや運用も）。`wiki/` はプロジェクトそのものの「いまこうなっている」の説明

### 受け箱（`inbox/`）

**まだどこにも属さない未整理のものの受け箱。** 行き先が決まっていないものを、出たらその場で、分かるだけの情報で置く。あとで棚卸しして、タスクや文書に移して空にする。プロジェクトごとに置く。

```markdown
---
about: ../tasks/2026-09-07-meal-planner.md     # 関係するタスクや文書。分かれば
---

# iOS でレシピ一覧が遅い気がする

スクロールのとき。再現条件は未確認。先週のリリース後から？
```

- 1 件 1 ファイル、`inbox/<YYYY-MM-DD>-<slug>.md`
- frontmatter は `about` だけで、それも任意。必須は見出し（か本文）だけ。不完全な情報が来る前提なので、分からない項目は書かず、AI も推測で埋めない
- AI が書くときは、人の言葉を言い換えない。人が後で読んで思い出せることが目的なので、人の言葉を残す
- 状態の項目は持たない。`inbox/` にあること自体が「未整理」の印
- **棚卸し**は、AI が 1 件ずつ行き先の候補を出し、人が決める。行き先は次のどれか

  | 中身 | 行き先 |
  | --- | --- |
  | やりたいこと、やるべきこと | `tasks/` のタスク |
  | あるタスクに関する情報 | そのタスクの `artifacts/` |
  | 作業で使う決まり・手順・事実 | `knowledge/` |
  | 指摘や、やり直しの気づき | `materials/` |
  | あとで参照したい情報 | `library/` |
  | 思い出せない、もう要らない | 消す |
  | まだ決められない | そのまま残す |

- 近いものとの違い: `artifacts/` は AI がタスクの作業中に書くもの（タスクに属し、archive に移る）。`materials/` は起きたこと（ナレッジの根拠）。`inbox/` はまだどこにも属さない未整理のもの

### 書庫（`library/`）

**あとで参照したい情報の控え。** 外の資料も、調べたり試したりして分かったことも、出たらその場で置く。書いた時点のもので、メンテしない。AI が要約とタグを付けて整理する。`inbox/` とは別に置くのは、空にするものと残すものを置き場所で分けるため。プロジェクトごとに置く。

何であるかは見出しと `url`・`source` で分かるようにし、本文は「内容」の節に置く。

```markdown
---
url: https://example.com/infinite-scroll-pitfalls   # あれば
source: 2026-11-10 の勉強会で聞いた話      # URL がないときの出どころ。自由な文（リンクではない）
tags: [pagination, frontend]
about: ../tasks/2026-11-09-printable-menu.md   # きっかけになったタスク。あれば
---

# 無限スクロールでハマりやすいところ

## 要約
（AI が書く。3〜5 行）

## 内容
（控えの本文。人の言葉は原文のまま）

## メモ
（人の一言があれば、そのまま。「献立の一覧で使えそう」など）
```

- 1 件 1 ファイル、`library/<YYYY-MM-DD>-<slug>.md`。frontmatter は全部任意で、必須は見出しだけ。「内容」「メモ」は中身があるときだけ置く。不完全でも置き、あとで分かったら足す
- 人の言葉は原文のまま残す。整理は、人の言葉を書き換えることではない
- `archive/` には移さない
- 読んで分かったことを作業に使う決まりにしたくなったら、ナレッジを足して `sources` でここを指す
- 近いものとの違い: タスクの中だけで使うものは `artifacts/`、作業の決まり（原則の当てはめ）は `knowledge/`、メンテし続ける成果物は `wiki/`。`library/` は、タスクを離れてもあとで参照したい事実を、書いた時点のまま残す

## 6. 原則・ナレッジ・素材

判断のよりどころは 3 層。**原則**（抽象的で根源的な考え方）← **ナレッジ**（原則をスコープに当てはめた決まり・手順・事実）← **素材**（ナレッジになる前の出来事）。下の層は上の層を相対パスで指す。

原則とナレッジは、**スコープが置き場所で決まる**。ルートのものは全プロジェクト、プロジェクトのディレクトリのものはそのプロジェクトだけに効く。ぶつかったらプロジェクトのものが勝つ。

| | 置き場所 | 1 件 | 読むとき | 時制 |
| --- | --- | --- | --- | --- |
| 原則 `principles/` | ルートとプロジェクト | `<slug>.md` | セッションの始めに本文を全部 | 知識 |
| ナレッジ `knowledge/` | ルートとプロジェクト | `<slug>.md` | 始めに `description`、要るときに本文 | 知識 |
| 素材 `materials/` | プロジェクトだけ | `<YYYY-MM-DD>-<slug>.md` | 蒸留するときだけ | 記録 |

### 原則（`principles/`）

ナレッジにないことでも同じ判断ができるようにするための、抽象的で根源的な考え方。少なく、めったに変わらない。追加と変更はユーザーに確認する。

```yaml
---
description: 不具合は症状を個別に塞がず、起きない構造にして直す
---
```

- ルートの原則は、どのプロジェクトでも通じる考え方
- プロジェクトの原則は、そのプロジェクトだけの考え方。本人が合わせる決まりや考え方が、そのプロジェクトだけ他と違うとき（チームが違うなど）に置く。読み手は変わらず本人と AI で、チームの人に見せるためのものではない
- 本文は、考え方・なぜ・適用の例を短く。セッションの始めにルートと作業中のプロジェクトの分を全部読むので、どちらも数ファイルに収める
- プロジェクトの原則がルートの原則を具体化したものなら、frontmatter の `principle` でルートの原則（`../../../principles/<名前>.md`）を指す。食い違うものなら、本文にどのルートの原則とどう違うかを 1 行書く

### ナレッジ（`knowledge/`）

AI が作業で使う決まり・手順・事実。1 件 1 ファイル。追加と変更はユーザーに確認する。プロジェクトで得た知識が他でも通用すると分かったら、ルートに移す（`desk mv`。指している・指されているリンクを付け替える）。

```yaml
---
description: 不具合やレビュー指摘を直すときに読む。症状を個別に塞がず、状態を入力に結び付けて「起きない形」にする
principle: [../principles/prefer-structure-over-patches.md, ../principles/single-source-of-truth.md]     # 1 つ以上。ルートの knowledge/ から見た相対パス
sources: [../projects/recipe-app/materials/2026-11-10-patched-each-error-screen.md, ../projects/recipe-app/tasks/2026-11-09-printable-menu.md]
---
```

- `description` は「いつ読むか」と「何が書いてあるか」を 1〜2 行で。これで読むかどうかが決まるので、いちばん丁寧に書く
- 必ず `principle` で、どの原則の当てはめかを指す（1 つ以上）。ひとつの場面に複数の原則が効くのは自然なので、1 つに絞らない。1 つなら文字列、複数ならリストで書く。指す先はルートの原則か、同じプロジェクトの原則。指せないなら、原則が足りないか、ナレッジの一般化が足りない
- `sources` で根拠（素材、決定）を指す。素材を消さないので、根拠はいつでもたどれる
- 本文は、決まり・なぜ・例 1 つ。詳細は別のファイルにして本文から指す。詳細のファイルには `principle` を書かない（どの原則の当てはめかは親が持つ）。ディレクトリは作らない
- そのスコープで成り立つ、いちばん一般的な形で書く。固有名は入れない（根拠は `sources` が指す）
- 確かめたが変えなかったときは、frontmatter の `verified` に今日の日付を書く（任意）。見直すのは、元になるものが変わったとき（operation.md 3.2）

**段階的に読む。** 全部を最初に読まない。

| 段 | 何を読むか | いつ |
| --- | --- | --- |
| 0 | ルートと作業中のプロジェクトの、全ナレッジの `description` | セッションの始め（原則の本文と一緒に） |
| 1 | 本文（決まり・なぜ・例 1 つ） | `description` が作業に当てはまるとき |
| 2 | 詳細（長い手順、背景、例） | 本文がリンクで指していて、要るとき |

切り出しは CLI がやる。段 0 は `desk ls knowledge --project <p> --level 0`、段 1 は `desk read <パス>`、段 2 は `desk read <パス> --level 2`（operation.md 3.5）。素の操作では「`description` だけ」が切り出しにくく、全部読んでしまう。

### 素材（`materials/`）

ナレッジになる前の出来事。ユーザーの指摘、レビューの指摘、やり直し、思っていたのと違ったこと。**起きたらその場で書く**（あとでまとめようとすると書かれない）。1 件 1 ファイルで、起きたプロジェクトの `materials/` に置く。ルートには置かない（まだ全体に適用できるか分からないもの）。

```markdown
---
source: ../tasks/2026-11-09-printable-menu.md   # 起きた場所。ツリーにあるときだけ書く
knowledge: []            # 蒸留してできた・足したナレッジ。空なら蒸留待ち
---

# エラー表示を画面ごとに個別に直した

## 何が起きたか
通信エラーで表示が崩れるのを画面ごとに個別に直したら、レビューで「共通のエラー表示に寄せれば 1 か所で済むのでは」と指摘された。

## 一般化の候補
- 同じ症状が複数の場所に出たら、個別に直す前に共通の原因を探す
```

- 1 件 1 ファイルなので、必要なだけ詳しく書ける（原文の引用、状況、なぜそうなったか、一般化の候補）。読むのは蒸留のときだけなので、溜まってもセッションの始めのトークンは増えない
- **蒸留**は、書いたその場でなくてよく、キリのいいところでやる。「どの原則の現れか」を考えてナレッジを足すか、既存のナレッジの `sources` に足し、素材の `knowledge` にそのナレッジを書く
- 蒸留した素材は消さずに残す（ナレッジの `sources` が指す根拠）。一般化する価値がないと決めた素材は消す（git にある）
- 全体で成り立つと分かったら、ルートのナレッジにする（素材はプロジェクトに残る）
- `archive/` には移さない

## 7. どの情報をどこに書くか

原則 3 の正本。同じことを 2 か所に書きたくなったら、ここに戻る。ここには情報と場所の対応だけを並べる。時制は原則 5 と場所ごとの節にある。

### タスクのこと

- タスクの目的と終わりの条件 → タスクの「目的」
- 人が知るべき進み具合 → タスクの「いま」
- PR と成果物の文書へのリンク。数行で済む本当に軽い中身 → タスクの「成果物」
- 人に判断してほしいこと・やってほしいこと → `needs_human: true` の子タスク
- 次の一手と、何を待っているか → タスクの「現在地」
- そのタスクの中だけの運用 → タスクの「決まり」
- 手順と進み具合 → タスクの「手順」
- ブランチ・base・worktree・PR → タスクの frontmatter か、手順の行
- タスクの親子・依存 → 子・後のタスクの frontmatter
- 決定・理由・却下した案、残す価値のある出来事 → タスクの「ログ」
- セッションでやったこと → git のコミット

### タスクの文書（`artifacts/`）

- 設計、調査の結果、レビューの結果など、タスクのための文書 → `artifacts/`
- 文書がどのタスクのものか → その文書の frontmatter `tasks`

### タスクを離れて残るもの

- プロジェクトの成果物としてメンテし続ける文書（仕組み、仕様、用語） → `wiki/`
- まだどこにも属さない未整理のもの（棚卸し前） → `inbox/`
- あとで参照したい情報の控え → `library/`

### 判断のよりどころ

- 抽象的で根源的な考え方 → ルートかプロジェクトの `principles/`
- 判断の決まり・手順・事実 → ルートかプロジェクトの `knowledge/`
- 指摘・やり直し・思っていたのと違ったこと → そのプロジェクトの `materials/`
- 永続の文書・ナレッジ・原則を、変えずに確かめた日 → その frontmatter の `verified`

### ツリーそのもの

- ツリーの決まり（形・書き方・手順） → スキル `desk`（仕組みのリポジトリの `skill/`）
- 何のツリー／プロジェクトか、どこに何があるか → README.md

### 書かないもの

- コードそのもの
- コミット履歴や PR の説明文の写し（URL だけ書く）
- 機密情報（認証情報、個人情報、本番データの実値）
- git と名前から分かること（日付、変更履歴）
- 中身のない節や文書

## 8. アーカイブ

タスクが終わったら（`done` か `dropped`）、そのタスクのものをプロジェクトの `archive/` に移す。

- **移すもの。** タスクのファイル（ログはその中）。そのタスクの `artifacts/`（とその `assets/`）の文書は、エージェントが選んで同じ操作にまとめて指定する（候補は `desk graph <タスク> --in` で出る）。自動では一緒に動かさない。他の文書から参照されているものや、単体で残したいものがあるため
- **移し方。** 複数のファイルを 1 回の `desk archive <パス>...` でまとめて動かす。`archive/` の中はプロジェクトと同じ形（`archive/tasks/`・`archive/artifacts/`・`archive/artifacts/assets/`）で、ファイル名は変えない。リンクは相対パスなので、**動かしたファイルの中のリンクと、動かしたファイルを指しているツリー中のリンクを付け替える。** まとめて動かせば付け替えも 1 回で済み、一緒に動くもの同士のリンク（文書→その `assets/`）は深さが変わらないのでそのまま。素でやるなら `git mv` のあと `grep -rl` で古いパスを探して直す。戻すのも同じ操作（`desk mv`）
- **いつ。** タスクを閉じるとき
- **移さないもの。** `wiki/`・`library/`・`principles/`・`knowledge/`・`materials/`（タスクを離れて生きるもの）。`inbox/` は棚卸しで空になるので、移すものがない
- **プロジェクトごと。** 終わったら、`projects/<p>/` を `archive/projects/<p>/` に移す（`desk archive --project`）。ルートの `archive/` の中も元と同じ形で、入るのは終わったプロジェクトだけ
- **タスクの置き場所は `status` から決まる。** 忘れてもいつやっても同じ。`done` で `archive/` の外に残っているタスクは直すべきもので、見つけたセッションが `desk archive` で移す（他のタスクのものはユーザーに確認してから。operation.md 3.1）。関連の文書の置き場所は `status` から導かず、`desk check` も挙げない
- **`archive/` 以外への移動も同じ。** ナレッジをルートへ、名前の変更など。`desk mv <元>... <先>` がリンクを付け替える

## 9. 一覧は手で書かない

手で保つ一覧は、正本（各ファイルの frontmatter と節）とずれていく。要るときに `desk ls` で、frontmatter と本文と git から出す。無くても `grep` で引ける。

- 動いているタスク: プロジェクト、名前、`status`、親、「いま」の 1 行目、最終更新（git）
- 人宛て: `needs_human: true` で動いているタスク（親と、目的の 1 行目）
- 蒸留待ち: `knowledge` が空の `materials/` のファイル
- 棚卸し待ち: `inbox/` のファイル全部（件数と見出し）
- 逆引き（子は？依存しているのは？このタスクの文書は？このナレッジの根拠は？）: `desk graph <パス> --in`（中身は `grep -rl '<ファイル名>'`）。frontmatter で絞るのは `desk ls`

## 10. 書き方の決まり

ドキュメントがごちゃごちゃになるのは、上書きすべきものに追記し、分けるべきものを 1 つに書き、経緯を本文に残すから。編集を繰り返しても崩れないように、次を守る。

1. **状態と知識は「最初からそうだった」形に書き直す。** 版や変更の経緯（「〜から変更」「以前は〜だったが」など）を書かない。版の違いは git、経緯はタスクのログの節にある
2. **記録は追記だけ、整理は別のファイルに。** 記録は並べ替えたり書き換えたりしない。整理したくなったら別のファイルに書き起こす
3. **経緯は書きすぎない。** 決定は結論と理由を 1〜3 行。会話の引用は要点だけ。やったことの羅列は git に任せる
4. **主題が増えたらファイルを分ける。** 1 ファイル 1 主題。別の主題が育ったら別のファイルに切り出す。1 つのファイルに節を足し続けない
5. **選択肢は決まったら消す。** 検討中の選択肢の表は、決まったら結論だけを残し、却下した案はログに 1 行書く
6. **古い内容は消す。** 役目を終えたものは消す。git にある
