# desk の構成

あらゆるプロジェクトとタスクのドキュメントを、浅いディレクトリと markdown の frontmatter で 1 つのツリーに一元管理する仕組み。ドキュメントのツリーと、仕組み（スキル・CLI・設計文書。このリポジトリ）は分けて置き、どちらも置き場所は決めない（9 節）。読み手はユーザー本人と AI だけで、他の人への引き継ぎ、個人とチームを分けるスコープ、git のリモートは考えない。

- **エージェントの入口はスキル `desk`**（`skill/SKILL.md`）。決まりの正本で、ツリーに触るエージェントは必ず読む
- **CLI `desk`**（`cli/`）は形（ディレクトリ・名前・frontmatter・節・リンク）を扱う補助ツールで、作る・引く・読む・確かめる・動かすをやる（skill-and-cli.md）
- **ルートの README.md は人向けの軽い概要。** 決まりの正本ではない
- **ナレッジの正本はこのツリー。** エージェントの memory の機能は使わない（正本が 2 つになる）

扱うもの: タスク（AI と人）と依存、調査、計画、作業の記録、レビュー、ブランチ・worktree・PR の構成、ナレッジとその素材、メモ、あとで参照したい情報の控え。

この文書は構成と書き方、skill-and-cli.md はスキルと CLI の設計。

---

## 1. 原則

細かい決まりは全部ここから導く。書いていないケースに出会ったら、ここに戻って判断する。

1. **プロジェクトはみな同じ形。ルートには全プロジェクトに適用するものだけを置く。** タスクとその文書は必ずどれかのプロジェクトにある。どのプロジェクトにも属さないタスクのために、なんでもありのプロジェクトを 1 つ置く
2. **ディレクトリは種類で分け、中はフラットに並べ、関係はリンクで表す。** 入れ子はプロジェクトの中で `<種類>/<ファイル>.md` の 2 段まで（例外は永続の文書 `wiki/` と、静的ファイルの `assets/` だけ）。親子・依存・「どのタスクの文書か」は frontmatter と本文のリンクで表す。リンクは相対パス
3. **1 つの事実は 1 か所に書く。** 他の場所からはリンクで指す。どこに何を書くかは 7 節の表が正本。これはこのツリーの中身の決まりで、スキルや CLI などツール側には当てはめない
4. **人に見せるものは短く、AI が使うものは詳しく。** 両方が少しずつなら同じファイルでよい。どちらも多いならファイルを分け、人向けからは AI 向けを指す
5. **時制を混ぜない。** 状態（いまどうか。上書きする）、記録（何があったか。追記だけする）、知識（次も使えること。磨いて書き換える）は別のファイルに書く。例外はタスクのファイルだけで、状態の節の下に記録の節（ログ）を 1 つ持つ
6. **ファイルは要るときに作り、中身のない節や文書は置かない。** 形はスキルに書いてあり（`desk new` が形どおりに作る）、雛形のディレクトリは置かない
7. **工程を状態にしない。** 調査中・設計中・レビュー待ちのような工程は進め方で変わるので、状態の語彙にしない
8. **git と名前で分かることは書かない。** 作成日はファイル名、変更の時系列と古い版は git にある

## 2. 全体の形

```
<ルート>/
├── .desk              # ルートの印（9 節）
├── README.md          # 人向けの軽い概要（何のツリーか、どこに何があるか、人向けの決まり 3 行）
├── principles/        # 全プロジェクトに通じる原則（6 節）
├── knowledge/         # 全プロジェクトで AI が使う知識（6 節）
├── archive/
│   └── projects/      # 終わったプロジェクト。中は projects/ と同じ形（8 節）
└── projects/
    ├── misc/          # どのプロジェクトにも属さないタスクを置く、なんでもありのプロジェクト
    └── <project>/     # 長く続く文脈（プロダクト・リポジトリ・領域）
        ├── README.md      # 何のプロジェクトか（人向けの概要。決まりは principles/ と knowledge/ に）
        ├── tasks/         # タスク。1 タスク 1 ファイル（4 節）
        ├── artifacts/     # タスクの文書とメモ。タスクと一緒に役目を終える（5 節）
        │   └── assets/    # 画像などの静的ファイル。文書のあるどのディレクトリにも置ける
        ├── wiki/          # プロジェクトの成果物としてメンテする文書。構成はプロジェクトで設計する（5 節）
        ├── inbox/         # まだどこにも属さない未整理のものの受け箱。棚卸しして空にする（5 節）
        ├── library/       # あとで参照したい情報の控え。書いた時点のまま残す（5 節）
        ├── principles/    # このプロジェクトだけの原則。本人が合わせる考え方がここだけ違うとき（6 節）
        ├── knowledge/     # このプロジェクトだけで AI が使う知識（6 節）
        ├── materials/     # ナレッジの素材。1 件 1 ファイル（6 節）
        └── archive/       # 終わったタスクのもの。中は上と同じ形（8 節）
```

- **ルートには全プロジェクトに適用するものだけ**を置く。人向けの概要、全体の原則とナレッジ。タスクとその文書はルートに置かない。プロジェクトは `projects/` にまとめ、ルートの中身とプロジェクトの名前が混ざらないようにする。雛形は置かず、形も決まりもスキルにあり、このツリーには置かない
- **プロジェクトは長く続く文脈。** 複数の PR にまたがる大きな作業はプロジェクトではなく、子を持つタスクにする。プロジェクトは `projects/` の下に平らに並べ、入れ子にしない。中身があるものだけ置く。なんでもありのプロジェクト（`projects/misc/`）も形は同じ
- **フラットの例外は `wiki/` だけ。** 構成をプロジェクトごとに設計するので、入れ子にしてよい
- **ルートに置くのは決まった名前だけ**: `.desk`・`README.md`・`principles/`・`knowledge/`・`assets/`・`archive/`・`projects/`。`projects/` の直下はプロジェクトのディレクトリだけ
- **どのディレクトリの中もフラット。** ファイル名は `<slug>.md`（タスク・素材・inbox・library は `YYYY-MM-DD-<slug>.md`）。識別はパスで、名前は同じ種類の中（`archive/` の同じ種類も含めて）で一意にする。ツリー全体で一意でなくてよい
- **リンクは相対パスで書く。** 本文は markdown のリンク `[文字](../artifacts/print-layout.md)`、frontmatter は同じ相対パスの文字列。基準はどちらもそのファイルの場所。絶対パスや `~` 始まりや名前だけのリンクは書かない。一般的なビューワーやエディタがそのまま開けることが目的。ファイルを動かしたら、動かしたファイルの中のリンクと、それを指しているリンクを付け替える（`desk archive`・`desk mv` がやる。8 節）。ログに書いた決定は、そのタスクのファイルへのパス（`../tasks/<タスク>.md`）で指す
- **画像などの静的ファイルは、文書と同じディレクトリの `assets/` に置く。** `artifacts/assets/`・`wiki/assets/`、README のものはプロジェクト直下やルートの `assets/`。中はフラットで、文書からは `assets/<ファイル>` の相対パスで指す。名前の決まりは置かない。どこからも指されていないものは `desk check` が挙げる。文書を `archive/` に移すとき、一緒に移すなら同じ `desk archive` にまとめて指定する（8 節）

## 3. 人が見るもの

人向けのものは、人が判断したり動いたりするのに要ることだけを、結論から簡潔に書く。細部は AI 向けの文書を指す。

| もの | 何を書くか |
| --- | --- |
| README.md（ルート・プロジェクト） | 人向けの軽い概要。何のツリー／プロジェクトか、どこに何があるか、人向けの決まり 3 行（9 節）。決まりの正本ではない（正本はスキル） |
| タスクのファイルの頭（目的・いま・成果物） | 4 節。人が読むのはここまで |
| 人が要るタスク（`needs_human: true`） | 人に判断・作業してほしいこと。4 節 |
| 人に見せる文書（`artifacts/`） | 設計書、仕様、レビュー結果など。タスクの「成果物」から指されているものが人向け。ファイルに印は付けない |
| 永続の文書（`wiki/`） | 5 節 |
| 受け箱（`inbox/`） | まだどこにも属さない未整理のものの受け箱。棚卸しで行き先を人が決める。5 節 |

人はタスク単位で成果物を見たいわけではないので、人の入口は **一覧（9 節）と `artifacts/`・`wiki/`** にする。タスクのファイルは、一覧から入って頭だけ読む。

## 4. タスク

### タスクは必ずファイル

`tasks/<YYYY-MM-DD>-<slug>.md`。1 タスク 1 ファイル。小さくてもファイルを作り、まとめて書くファイルは置かない。どのプロジェクトにも属さないタスクは、なんでもありのプロジェクト（`projects/misc/`）に置く。

タスクと手順の区別:

- **タスク**（ファイル）: 終わりの条件があって、ブランチ・PR・別のセッション・人への依頼のどれかを持つもの
- **手順**（タスクのファイルの中の行）: そのタスクの中で順にやるだけのこと。チェックボックスで書く。手順がタスクの条件を満たすようになったら、ファイルに切り出して、行は `→ [子の見出し](<子のファイル>.md)` に置き換える

### ファイルの形

```markdown
---
status: inprogress        # backlog / todo / inprogress / done / dropped
needs_human: false        # false / true
parent: 2026-09-07-meal-planner.md                           # 同じ tasks/ の中なのでファイル名だけ
depends_on: [2026-10-14-meal-planner-shopping-list.md]
repo: ~/src/recipe-app
branch: feature/meal-planner/printable-menu   # base: feature/meal-planner/all
worktree: ~/src/recipe-app-worktrees/meal-planner
pr: https://github.com/example/recipe-app/pull/128
---

# 献立を印刷できるようにする

## 目的
3 行まで。終わりの条件を含む。

## いま
人が知るべき粒度で 3 行まで。人にとって意味のある変化のときだけ書き換える。

## 成果物
- PR: #128, #129, recipe-api #42
- [印刷のレイアウト](../artifacts/print-layout.md)

## 現在地
次の一手と、何を待っているか。セッションごとに上書きする。

## 決まり
このタスクの中だけの運用（ブランチの切り方、確認のしかたなど）。

## 手順
- [x] 献立を印刷用の形に並べる
- → [印刷のプレビューを出す](2026-11-11-print-preview.md)
- → [用紙の大きさを決める](2026-11-10-decide-paper-size.md)
- [ ] レビューの指摘 1〜4 に返信する

## ログ
### 2026-11-10
- 決定: 印刷用のページは画面と別に作る。理由: 画面をそのまま印刷すると、ボタンやメニューまで出る
- 試してやめた: 画面に印刷用のスタイルを当てるだけにする。1 週間分が 1 枚に収まらなかった
```

- **頭の 3 節（目的・いま・成果物）は人向け**、現在地・決まり・手順は AI 向けの状態、いちばん下のログは記録。タスクは人向けの量が少ないので同じファイルに置く（原則 4）
- **frontmatter** は `status` と `needs_human` が必須。`parent`・`depends_on` はタスクのファイルへの相対パス（同じ `tasks/` ならファイル名だけ）。`repo` と `worktree` は `~` からのパスで書く（このツリーはコードリポジトリと別の場所にあるので、相対パスにしない）。ブランチ・base・worktree・PR はタスクが 1 本の枝を持つときに書く。複数の枝を持つなら、子タスクに分けるか、手順の行の末尾に書く。正本はこのファイルだけ
- **`needs_human`** は人の判断か作業が要るか。誰がやるかではないので、`false` のタスクを人がやってもよい
- **`status`** は `backlog`（やるか決めていない・いつか）、`todo`（やると決めた・未着手）、`inprogress`（着手している）、`done`、`dropped`。待っていることは `depends_on` で表す。工程は書かない（原則 7）
- **親子**は子の `parent` で表す。親のファイルには子を列挙しない。順序や依存を示したいときだけ、親の手順に `→ [子](<子のファイル>.md)` の行を置く（チェックボックスは付けず、状態は子にだけ持つ）
- **依存**は後のタスクの `depends_on` にだけ書く。逆向きは検索で引く
- **成果物**は PR と人に見せる文書へのリンク。数行で済む本当に軽い中身（確認の結果など）だけは、ファイルを作らずに直接書いてよい（そのためだけのファイルは、人が開く手間を増やすだけ）

### ログ（タスクのファイルの最後の節）

そのタスクの決定と経緯を、タスクのファイルのいちばん下の「ログ」の節に、日付の小見出しで追記だけする。別のファイルにしない。1 セッション 1 ファイルの作業ログも作らない。要るときに節を作る。

- 書くもの: 決定（`決定:` で始め、理由と却下した案を添える）、残す価値のある出来事
- 書かないもの: やったことの羅列（git のコミットにある）、次の一手（現在地にある）、人に聞くこと（人が要るタスクにある）
- 決定は、それを書いたタスクのファイルへの相対パスで指す（`../tasks/<タスクの名前>.md`）。指すのはファイルまで
- 上の節は上書き、この節は追記だけ（原則 5 の例外。同じファイルに置くのは、タスクが終われば一緒に役目を終え、別に引く場面が無いため）。人はここを読まなくてよい。長くなってきたら、それはタスクが大きすぎる印なので子タスクに分ける
- `desk read <タスク> --section 目的,いま,決まり` のように節で切れば、ログを読まずに済む

### 人が要るタスク

人に判断してほしいこと（確認）も、人がやる作業も、**そのタスクの子タスクとして切り出し、`needs_human: true` を付ける。** 形は同じ。こうすると、確認を待っているタスクは `depends_on` で、確認の中身は子タスクのファイルで、答えは子タスクの成果物で、全部タスクの仕組みに載る。

```markdown
---
status: todo
needs_human: true
parent: 2026-11-09-printable-menu.md
---

# 用紙の大きさを決める

## 目的
a A4 だけ / b A4 と B5 / c 使う人が選ぶ。おすすめ a（家庭のプリンターはほとんど A4）。

## 成果物
- 決定: [献立を印刷できるようにする](2026-11-09-printable-menu.md) のログ
```

- 目的に、聞きたいことと選択肢とおすすめを書く
- 答えが出たら、決定は親（聞いたタスク）のログに書き、子の成果物からそれを指して `done` にする
- **人宛ての一覧**は `needs_human: true` で動いているタスクを集めて出す（9 節）。手で保つ受け箱は置かない

## 5. 文書・メモ

| ディレクトリ | 何か | 時制 | 読み手 | 構造 | タスクが終わったら |
| --- | --- | --- | --- | --- | --- |
| `artifacts/` | タスクの文書とメモ | 状態（整理した文書）か記録（溜めるメモ）。ファイルごと | 人と AI | フラット | `archive/` へ |
| `wiki/` | プロジェクトの成果物としてメンテする文書 | 知識 | 人と AI | プロジェクトで設計する | 残してメンテする |
| `inbox/` | まだどこにも属さない未整理のもの。棚卸しして移す | 受け箱 | 人と AI | フラット | （タスクに属さない。棚卸しで空になる） |
| `library/` | あとで参照したい情報の控え。書いた時点のまま残す | 記録 | 人と AI | フラット | （タスクに属さない。残す） |

### `artifacts/`（タスクの文書とメモ）

タスクのための**整理した文書**と**溜めるメモ**を、同じディレクトリに置く。どれも使い捨て。タスクが終われば `archive/` に移す。人に見せるものも、AI だけが読むものも置く。

- 名前は中身で付ける。frontmatter の `tasks` で、どのタスクのための文書かを指す（複数でもよい。仕様を複数の PR で使うなど）
- 整理した文書は結論から書き、新しく分かったら最初からそうだったように書き直す。溜めるメモは 1 テーマ 1 ファイルで追記し、整理しない（10 節）。どちらかはファイルごとに決まり、ディレクトリでは分けない
- 人に見せるものは、タスクの「成果物」から指す。印は付けない

```yaml
---
tasks: [../tasks/2026-11-09-printable-menu.md]
---
```

- 画像や図は `artifacts/assets/` に置き、`![](assets/print-sample.png)` で指す（2 節）

### `wiki/`（永続の文書）

仕組みの説明、仕様、用語など、**プロジェクトの成果物としてメンテし続ける文書。** コードリポジトリの中の docs と同じ扱いで、プロジェクトごとに構成を設計して使う。タスクには属さない。人も AI も読む。置き場所に困ったものの受け皿ではなく、使わないプロジェクトがあってよい。タスクの文書（`artifacts/`）とは別のディレクトリに置き、ここにあるものは全部メンテの対象だと置き場所で言い切れるようにする。

- **構成はプロジェクトごとに設計する。** 入れ子にしてよい（フラットの唯一の例外）
- 特定のタスクの話は、そのタスクが終わっても残すもの（保守に要るなど）だけ置く。タスクに紐づく文書は、大きなタスクの進め方のようなものも、そのタスクの `artifacts/` に置く
- 各ファイルの frontmatter に `description`（何が書いてあるか、いつ読むか）を書く。確かめたが変えなかったときは `verified`（その日付）も書く（任意）。AI は `description` を集めて、関係するものだけ読む（ナレッジの段 0 と同じ）
- **メンテし続けられる量だけ持つ。** 古いだけの文書は問題にしない（中身が正しければそのままでよい）
- 最初からそうだったように書き直す（10 節）。経緯は書かない
- `archive/` には移さない。プロジェクトが終わるときにプロジェクトごと移る
- 近いものとの違い: `artifacts/` はタスクのため（使い捨て。大きなタスクの進め方も、そのタスクの文書）、`knowledge/` は AI が作業で使う決まり・手順・事実（短く、原則に紐づく。特定のタスクに限らない開発の流れや運用も）。`wiki/` はプロジェクトそのものの「いまこうなっている」の説明

### `inbox/`（受け箱）

**まだどこにも属さない未整理のものの受け箱。** 行き先が決まっていないものを、出たらその場で、分かるだけの情報で置く。あとで棚卸しして、タスクや文書に移して空にする。プロジェクトごとに置く。

```markdown
---
about: ../tasks/2026-09-07-meal-planner.md     # 関係するタスクや文書。分かれば
---

# iOS でレシピ一覧が遅い気がする

スクロールのとき。再現条件は未確認。先週のリリース後から？
```

- 1 件 1 ファイル、`inbox/<YYYY-MM-DD>-<slug>.md`
- **frontmatter は `about` だけで、それも任意。** 必須は見出し（か本文）だけ。不完全な情報が来る前提なので、分からない項目は書かず、AI も推測で埋めない
- **AI が書くときは、人の言葉を言い換えない。** 人が後で読んで思い出せることが目的なので、人の言葉を残す
- **棚卸し**は、AI が 1 件ずつ行き先の候補を出し、人が決める。行き先は次のどれか。`inbox/` にあること自体が「未整理」の印なので、状態の項目は持たない

  | 中身 | 行き先 |
  | --- | --- |
  | やりたいこと、やるべきこと | `tasks/` のタスク |
  | あるタスクに関する情報 | そのタスクの `artifacts/` |
  | 作業で使う決まり・手順・事実 | `knowledge/` |
  | 指摘や、やり直しの気づき | `materials/` |
  | あとで参照したい情報 | `library/` |
  | 思い出せない、もう要らない | 消す |
  | まだ決められない | そのまま残す |

- 近いものとの違い: `artifacts/` は AI がタスクの作業中に書くもの（タスクに属し、archive に移る）。`materials/` は起きたこと（ナレッジの根拠）。`inbox/` はまだどこにも属さない未整理のもの

### `library/`（書庫）

**あとで参照したい情報の控え。** 外の資料も、調べたり試したりして分かったことも、出たらその場で置く。書いた時点のもので、メンテしない。AI が要約とタグを付けて整理する。`inbox/` とは別に、プロジェクトごとに置く。空にするものと残すものを置き場所で分けるため。

**何であるかは見出しと `url`・`source` で分かるようにし、本文は「内容」の節に置く。**

```markdown
---
url: https://example.com/infinite-scroll-pitfalls   # あれば
source: 2026-11-10 の勉強会で聞いた話      # URL がないときの出どころ。自由な文
tags: [pagination, frontend]
about: ../tasks/2026-11-09-printable-menu.md   # きっかけになったタスク。あれば
---

# 無限スクロールでハマりやすいところ

## 要約
（AI が書く。3〜5 行）

## 内容
（控えの本文。人の言葉は原文のまま）

## メモ
（人の一言があれば、そのまま。「献立の一覧で使えそう」など）
```

- 1 件 1 ファイル、`library/<YYYY-MM-DD>-<slug>.md`。frontmatter は全部任意で、必須は見出しだけ。不完全でも置き、あとで分かったら足す
- **人の言葉は原文のまま残す。** 整理は、人の言葉を書き換えることではない
- `archive/` には移さない
- 読んで分かったことを作業に使う決まりにしたくなったら、ナレッジを足して `sources` でここを指す
- 近いものとの違い: タスクの中だけで使うものは `artifacts/`（溜めるメモ）、作業の決まり（原則の当てはめ）は `knowledge/`、メンテし続ける成果物は `wiki/`。`library/` は、タスクを離れてもあとで参照したい事実を、書いた時点のまま残す

## 6. 原則・ナレッジ・素材

判断のよりどころは 3 層。**原則**（抽象的で根源的な考え方）← **ナレッジ**（原則をスコープに当てはめた決まり・手順・事実）← **素材**（ナレッジになる前の出来事）。下の層は上の層を相対パスで指す。原則とナレッジは、**スコープが置き場所で決まる**: ルートは全プロジェクト、プロジェクトのディレクトリはそのプロジェクトだけ。

| | 置き場所 | 1 件 | 読むとき | 時制 |
| --- | --- | --- | --- | --- |
| 原則 `principles/` | ルートとプロジェクト | `<name>.md` | セッションの始めに本文を全部 | 知識 |
| ナレッジ `knowledge/` | ルートとプロジェクト | `<name>.md` | 始めに `description`、要るときに本文 | 知識 |
| 素材 `materials/` | プロジェクトだけ | `<YYYY-MM-DD>-<slug>.md` | 蒸留するときだけ | 記録 |

### 原則（`principles/`）

ナレッジにないことでも同じ判断ができるようにするための、抽象的で根源的な考え方。少なく、めったに変わらない。追加と変更はユーザーに確認する。

- **ルートの原則**は、どのプロジェクトでも通じる考え方
- **プロジェクトの原則**は、そのプロジェクトだけの考え方。本人が合わせる決まりや考え方が、そのプロジェクトだけ他と違うとき（チームが違うなど）に置く。読み手は変わらず本人と AI で、チームの人に見せるためのものではない。ルートの原則と食い違う場合は、プロジェクトの原則が勝つ（そのプロジェクトではそちらに従う）

```yaml
---
description: 不具合は症状を個別に塞がず、起きない構造にして直す
---
```

- 本文は、考え方・なぜ・適用の例を短く。セッションの始めにルートと作業中のプロジェクトの分を全部読むので、どちらも数ファイルに収める
- プロジェクトの原則が、ルートの原則を具体化したものなら frontmatter の `principle` でルートの原則（`../../../principles/<名前>.md`）を指す。食い違うものなら、本文にどのルートの原則とどう違うかを 1 行書く

### ナレッジ（`knowledge/`）

AI が作業で使う決まり・手順・事実。1 件 1 ファイル。**スコープは置き場所で決まる**: ルートの `knowledge/` は全プロジェクト、プロジェクトの `knowledge/` はそのプロジェクトだけ。プロジェクトで得た知識が他でも通用すると分かったら、ルートに移す（`desk mv`。指している・指されているリンクを付け替える）。

```yaml
---
description: 不具合やレビュー指摘を直すときに読む。症状を個別に塞がず、状態を入力に結び付けて「起きない形」にする
principle: [../principles/prefer-structure-over-patches.md, ../principles/single-source-of-truth.md]     # 1 つ以上。ルートの knowledge/ から見た相対パス
sources: [../projects/recipe-app/materials/2026-11-10-patched-each-error-screen.md, ../projects/recipe-app/tasks/2026-11-09-printable-menu.md]
---
```

**段階的に読む。** スキルと同じで、全部を最初に読まない。

| 段 | 何を読むか | いつ |
| --- | --- | --- |
| 0 | ルートと作業中のプロジェクトの、全ナレッジの `description` | セッションの始め（原則の本文と一緒に） |
| 1 | 本文（決まり・なぜ・例 1 つ） | `description` が作業に当てはまるとき |
| 2 | 詳細（長い手順、背景、例） | 本文がリンクで指していて、要るとき |

切り出しは CLI がやる。段 0 は `desk ls knowledge --project <p> --level 0`、段 1 は `desk read <パス>`、段 2 は `desk read <パス> --level 2`（skill-and-cli.md 2.5）。素の操作では「`description` だけ」が切り出しにくく、全部読んでしまう。

- **必ず `principle` でどの原則の当てはめかを指す（1 つ以上）。** ひとつの場面に複数の原則が効くのは自然なので、1 つに絞らない。1 つなら文字列、複数ならリストで書く。指す先はルートの原則か、同じプロジェクトの原則。指せないなら、原則が足りないか、ナレッジの一般化が足りない
- `description` は「いつ読むか」と「何が書いてあるか」を 1〜2 行で。これで読むかどうかが決まるので、いちばん丁寧に書く
- `sources` で根拠（素材、決定）を指す。素材を消さないので、根拠はいつでもたどれる
- 詳細は別のファイルにして本文から指す。詳細のファイルには `principle` を書かない（どの原則の当てはめかは親が持つ）。ディレクトリは作らない
- 確かめたが変えなかったときは、frontmatter の `verified` に今日の日付を書く（任意）。見直すのは、元になるものが変わったとき（skill-and-cli.md 2.2）
- そのスコープで成り立つ、いちばん一般的な形で書く。固有名は入れない（根拠は `sources` が指す）
- ぶつかったら、プロジェクトのナレッジが勝つ（原則と同じ）

### 素材（`materials/`）

ナレッジになる前の出来事。ユーザーの指摘、レビューの指摘、やり直し、思っていたのと違ったこと。**起きたらその場で書く**（あとでまとめようとすると書かれない）。1 件 1 ファイルで、起きたプロジェクトの `materials/` に置く。ルートには置かない（まだ全体に適用できるか分からないもの）。

```markdown
---
source: ../tasks/2026-11-09-printable-menu.md   # 起きた場所。ツリーにあるときだけ書く
knowledge: []            # 蒸留してできた・足したナレッジ。空なら蒸留待ち
---

# エラー表示を画面ごとに個別に直した

## 何が起きたか
通信エラーで表示が崩れるのを画面ごとに個別に直したら、レビューで「共通のエラー表示に寄せれば 1 か所で済むのでは」と指摘された。

## 一般化の候補
- 同じ症状が複数の場所に出たら、個別に直す前に共通の原因を探す
```

- 1 件 1 ファイルなので、必要なだけ詳しく書ける（原文の引用、状況、なぜそうなったか、一般化の候補）。読むのは蒸留のときだけなので、溜まってもセッションの始めのトークンは増えない
- **蒸留**は、書いたその場でなくてよく、キリのいいところでやる。「どの原則の現れか」を考えてナレッジを足すか、既存のナレッジの `sources` に足し、素材の `knowledge` にそのナレッジを書く
- 蒸留した素材は消さず残す（ナレッジの `sources` が指す根拠）。一般化する価値がないと決めた素材は消す（git にある）
- 全体で成り立つと分かったら、ルートのナレッジにする（素材はプロジェクトに残る）
- `archive/` には移さない

## 7. どの情報をどこに書くか

原則 3 の正本。同じことを 2 か所に書きたくなったら、ここに戻る。

| 情報 | 書く場所 | 読み手 | 時制 |
| --- | --- | --- | --- |
| タスクの目的・終わりの条件 | タスク「目的」 | 人 | 状態 |
| 人が知るべき進み具合 | タスク「いま」 | 人 | 状態 |
| 成果物（PR・人に見せる文書）へのリンク。本当に軽い中身はそのまま | タスク「成果物」 | 人 | 状態 |
| 人に判断してほしいこと・やってほしいこと | `needs_human: true` の子タスク | 人 | 状態 |
| 人に見せる結論（設計、レビュー結果など） | `artifacts/` | 人 | 状態 |
| 次の一手・何を待っているか | タスク「現在地」 | AI | 状態 |
| タスクの中だけの運用 | タスク「決まり」 | AI | 状態 |
| 手順と進み具合 | タスク「手順」 | AI | 状態 |
| ブランチ・base・worktree・PR | タスクの frontmatter か手順の行 | AI | 状態 |
| タスクの親子・依存 | 子・後のタスクの frontmatter | AI | 状態 |
| 文書・メモがどのタスクのものか | 文書・メモの frontmatter `tasks` | AI | 状態 |
| AI が後で読むために整理したこと | `artifacts/`（成果物には載せない） | AI | 状態 |
| プロジェクトの成果物としてメンテする文書（仕組み、仕様、用語） | `wiki/` | 人と AI | 知識 |
| 決定・理由・却下した案 | タスク「ログ」 | AI | 記録 |
| 残す価値のある出来事 | タスク「ログ」 | AI | 記録 |
| セッションでやったこと | git のコミット | AI | 記録 |
| 調査のデータ・作業用のメモ | `artifacts/`（溜めるメモ） | AI | 記録 |
| まだどこにも属さない未整理のもの（棚卸し前） | `inbox/` | 人と AI | 受け箱 |
| あとで参照したい情報の控え | `library/` | 人と AI | 記録 |
| 指摘・やり直し・思っていたのと違ったこと（ナレッジの根拠） | プロジェクトの `materials/` | AI | 記録 |
| 判断の決まり・手順・事実 | `knowledge/` | AI | 知識 |
| 抽象的で根源的な考え方 | `principles/`（全体はルート、プロジェクトだけのものはプロジェクト） | AI | 知識 |
| ツリーの決まり（形・書き方・手順） | スキル `desk`（このリポジトリの `skill/`。CLI は同じ形を実装する） | AI | 知識 |
| ツリー・プロジェクトの人向けの概要 | README.md | 人 | 知識 |
| 永続の文書・ナレッジ・原則を、変えずに確かめた日（任意） | frontmatter `verified` | AI | 状態 |

## 8. アーカイブ

タスクが終わったら（`done` か `dropped`）、そのタスクのものをプロジェクトの `archive/` に移す。

- **移すもの**: タスクのファイル（ログはその中）。そのタスクの `artifacts/`（とその `assets/`）の文書は、エージェントが選んで同じ操作にまとめて指定する（候補は `desk graph <タスク> --in` で出る）。自動では一緒に動かさない: 他の文書から参照されているもの、単体で残したいものがあるため
- **移し方**: 複数のファイルを 1 回の `desk archive <パス>...` でまとめて動かす。`archive/` の中はプロジェクトと同じ形（`archive/tasks/`・`archive/artifacts/`・`archive/artifacts/assets/`）。ファイル名は変えない。リンクは相対パスなので、**動かしたファイルの中のリンクと、動かしたファイルを指しているツリー中のリンクを付け替える**。まとめて動かせば付け替えも 1 回で済み、一緒に動くもの同士のリンク（文書→その `assets/`）は深さが変わらないのでそのまま。素でやるなら `git mv` のあと `grep -rl` で古いパスを探して直す。戻すのも同じ操作（`desk mv`）
- **いつ**: タスクを閉じるとき。子を持つタスクは、子を含めて親が終わるときにまとめて移してもよい
- **移さないもの**: `wiki/`・`library/`・`principles/`・`knowledge/`・`materials/`（タスクを離れて生きるもの）。`inbox/` は棚卸しで空になるので移すものがない
- プロジェクトごと終わったら、`projects/<p>/` を `archive/projects/<p>/` に移す（`desk archive --project`）。プロジェクトの中の `archive/` と同じく、ルートの `archive/` の中は元と同じ形で、入るのは終わったプロジェクトだけ
- タスクの置き場所は `status` から決まるので、忘れてもいつやっても同じ。`done` で `archive/` の外に残っているタスクは直すべきもので、見つけたセッションが `desk archive` で移す（他のタスクのものはユーザーに確認してから。skill-and-cli.md 2.1）。関連の文書の置き場所は `status` から導かず、`desk check` も挙げない
- `archive/` 以外への移動（ナレッジをルートへ、名前の変更）も同じで、`desk mv <元>... <先>` がリンクを付け替える

## 9. 運用

### 道具（スキルと CLI）

正本はファイルと git で、人も AI も直接読み書きする。エージェントの入口はスキル `desk`、補助は Go の CLI `desk`。設計は skill-and-cli.md。

- **置き場所は決めない。** ツリーはどこに置いてもよく、ルートに印のファイル `.desk` を置く（`desk init` が作る）。CLI は、作業ディレクトリから上にたどって `.desk` のあるディレクトリをルートにし、見つからなければ（ツリーの外では）何も書き換えずにエラーで止まる。`desk root` がいまのルートを出す。仕組みのリポジトリもどこに置いてもよく、スキルは `skill/` をエージェントのスキルの場所にリンクし、CLI は `go install` で入れる。ツリーにも仕組みにも、どちらの場所も書き込まない

- **スキルは、ツリーに触るエージェントが読む。** 誰が読んで誰に伝えるかは決めない（エージェントの使い方やオーケストレーションの組み方はユーザーの自由）。エージェントの memory の機能は使わないので、このツリーが読まれる入口はこのスキルだけ
- **決まりの正本はスキルで、スキルは必須。** 形も書き方も手順もスキルに書き、CLI は同じ形を実装する（ツール側で二重になるのは構わない。「1 つの事実は 1 か所」はこのツリーの中身の決まり）。README は人向けの概要。設計文書はこのリポジトリの `docs/` に置く
- **CLI は形を扱う補助ツール。** 形どおりに作る `init`・`new`、形で引く `ls`・`graph`、必要な深さだけ読む `read`、形に合っているか確かめる `check`（機械的な直しは `--fix`）、リンクを付け替えながら動かす `archive`・`mv`。中身を書く、何を読むか決める、外の世界と突き合わせる、コミットする、はエージェント。CLI を通さないと書けない、という強制はしない。無くても手でできる（「概要だけ読む」だけは `cat` で全部読むことになる）
- **守るのは内容の不整合で、放置ではない。** 触られていない文書は中身が正しければそのままでよい。作業は進んでいるのに文書が古い、ファイル同士が食い違う、外の世界（PR・ブランチ）と食い違う、は直すべきもので、しきい値や定期の点検を待たない。進めた側がそのとき直す。他のタスクの分を見つけたら、本来のタスクをそっちのけにせず、ユーザーに伝えて確認が取れたら直す（skill-and-cli.md 2.1）。直近の作業がぶつかって起きたずれは別の話で、下の「同時に書くとき」。archive への移動は `status` から決まるので、忘れてもいつやっても同じ
- **同時書き込みは厳密に防がず、後から直す。** 壊れにくい書き方 3 つ（置換で書く、`git add` はパス指定で小さくコミット、相手の作業は勝手に直さない）と、気づく場所 2 つ、直すのは誰かを決める基準 3 つで判断する（下の「同時に書くとき」）
- **人も直接書く。** 形を守らなくてよく、コミットもしなくてよい。合わせるのはエージェント側（下の「人が直接書くとき」）

### セッションの始めに読むもの

1. プロジェクトの README.md（何のプロジェクトか。短い）。決まりはスキルにあるので、README を決まりとして読まない
2. ルートと作業中のプロジェクトの、原則の本文（`desk ls principle --project <p> --level 1`）と、ナレッジの段 0（`desk ls knowledge --project <p> --level 0`）
3. タスクのファイル。親があれば親の頭と決まり（`desk read <親> --section 目的,いま,決まり`）
4. `tasks` でこのタスクを指す `artifacts/`（溜めるメモは要るときだけ）と、`description` が関係する `wiki/`
5. 作業に合わせてナレッジの段 1・段 2（`desk read <パス>`、`--level 2`）

### セッションの終わりにやること

1. タスクの現在地と手順を直す
2. 決めたことと、残す価値のある出来事をタスクのログの節に追記する
3. 人にとって意味のある変化があったときだけ、「いま」と「成果物」を直す
4. このタスクで変わったことを書いている文書があれば直す。確かめて正しければそのままでよい（`verified` は任意）。タスクを閉じるなら、一緒に移す文書を選んで `desk archive <タスク> <文書>...`（`status` を書き、リンクを付け替えて同じ形で移す）で `archive/` に移し、その変更だけを先にコミットする
5. `inbox/` に未整理が溜まっていたら棚卸しを提案する（誰がやるかは決めない）
6. 自分のタスクのファイルだけを `git add <パス>...` して 1 コミット。`docs(<タスクの名前>): <一言>`、本文にやったことを 1〜3 行。`git add -A` は使わない。人の未コミットの変更が残っていれば、別のコミットで取り込む

### 同時に書くとき

複数のセッションが同じツリーを書く。厳密には防がず、壊れにくい書き方を守り、壊れたら git を頼りに直す（詳しくは skill-and-cli.md 2.3）。

- **1 つのタスクを同時に書くのは 1 つのセッション。** 並べて進める作業は子タスクに分ける。誰がどのタスクを持つかはツリーに書かない
- **既存のファイルは全体を書き直さず、該当箇所の置換で直す。** 置換元が変わっていれば失敗して、古い理解で上書きしたことに気づける。追記は末尾だけ
- **git は `git add <パス>...` だけ。** `git add -A` を使わない。小さくこまめにコミットする
- **相手の作業は勝手に直さない。** 他のタスクのファイルと相手が書いた中身は触らない
- **テキストが衝突しなくても中身はずれる**（archive に移した後に古いパスへ追記する、`wiki/` の値を直した直後に古い値を前提の文書を書く）。1 つの事実は 1 か所（7 節）なので直す場所は 1 つで済む。名前の重複は見つけたら 1 つに寄せるか名前を変える
- **ずれに気づく場所は 2 つ。** 書く直前の読み直しと、コミット直後の `git log`（自分の触ったファイルに他のタスクのコミットが混ざっていないか）。意味のずれは次に読むエージェントが気づく（skill-and-cli.md 2.3）
- **直すのは誰かの基準は 3 つ。** 不整合を含むコミットを入れた側が直す（順番ではなく、どのコミットに入ったかで決まる）。相手の作業は勝手に直さず、ユーザーに伝え、確認が取れたら直してよい。相手側にも直しが要るなら、相手自身がこちらの直しが済んでから対応する（skill-and-cli.md 2.3）。放置・形骸化した反映漏れは別の話（skill-and-cli.md 2.1）
- **ワーキングツリーは 1 本で `main` に直接コミット。** ブランチや worktree を分けると、他のセッションの変更が見えない間に古い理解で書き、マージで行は通るのに中身がずれる

### 人が直接書くとき

人はエディタで直接書く。形を守らなくてよく、コミットもしなくてよい。人向けの決まりは README に 3 行だけ: どこに書いてもよい、迷ったら `inbox/`、コミットはしなくてよい。合わせるのはエージェント側（skill-and-cli.md 2.4）。

- エージェントが読むのは作業ツリー。人の未コミットの変更はそのまま正として読む
- 人の未コミットの変更は自分のコミットに混ぜない。セッションの終わりに残っていれば、別のコミット（`docs(<タスク>): 人の編集を取り込む`）で取り込む
- 人が最近触ったファイルは、できるだけ書かない。書いたら伝える
- 人の未コミットの変更に、直近のコミットで足した内容の削除が含まれていたら（古いバッファの保存で消えた疑い）、意図した削除か人に聞く
- 形がずれたファイルは `desk check` が挙げるので、見つけたエージェントが整える（機械的なものは `--fix`）。文面は人の言葉を書き換えない

### 一覧（ビュー）

手で書く一覧は置かない。手で保つ一覧は、正本（各ファイルの frontmatter と節）とずれていく。要るときに `desk ls` で frontmatter と本文と git から出す。無くても `grep` で引ける。

- 動いているタスク: プロジェクト、名前、`status`、親、「いま」の 1 行目、最終更新（git）
- 人宛て: `needs_human: true` で動いているタスク（親と、目的の 1 行目）
- 蒸留待ち: `knowledge` が空の `materials/` のファイル
- 棚卸し待ち: `inbox/` のファイル全部（件数と見出し）
- 逆引き（子は？依存しているのは？このタスクの文書は？このナレッジの根拠は？）: `desk graph <パス> --in`（中身は `grep -rl '<ファイル名>'`）。frontmatter で絞るのは `desk ls`

### 書かないもの

- コードそのもの、コミット履歴や PR の説明文の写し（URL だけ書く）
- 機密情報（認証情報、個人情報、本番データの実値）
- git と名前から分かること（日付、変更履歴）
- 中身のない節や文書

## 10. 書き方の決まり（編集を繰り返しても崩れないために）

ドキュメントがごちゃごちゃになるのは、上書きすべきものに追記し、分けるべきものを 1 つに書き、経緯を本文に残すから。次を守る。

1. **状態と知識は「最初からそうだった」形に書き直す。** 版や変更の経緯（「〜から変更」「以前は〜だったが」など）を書かない。版の違いは git、経緯はタスクのログの節にある
2. **記録は追記だけ、整理は別のファイルに。** 記録は並べ替えたり書き換えたりしない。整理したくなったら別のファイルに書き起こす
3. **経緯は書きすぎない。** 決定は結論と理由を 1〜3 行。会話の引用は要点だけ。やったことの羅列は git に任せる
4. **主題が増えたらファイルを分ける。** 1 ファイル 1 主題。別の主題が育ったら別のファイルに切り出す。1 つのファイルに節を足し続けない
5. **選択肢は決まったら消す。** 検討中の選択肢の表は、決まったら結論だけを残し、却下した案はログに 1 行書く
6. **古い内容は消す。** 役目を終えたものは消す。git にある
7. **人向けは短く保つ。** 細部は AI 向けの節や文書に下ろす
