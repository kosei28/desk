# スキルと CLI の設計

desk のツリーを人と AI エージェントが壊さずに使い続けるための、スキル `desk` と CLI `desk` の設計。ツリーの形と書き方は design.md。

**前提。**

- 正本はファイルと git。人もエージェントも直接読み書きする。エージェントの使い方（セッションの数、オーケストレーションの組み方）は決めない
- **CLI は「形」を扱い、エージェントは「中身」を扱う。** 形（ディレクトリ、ファイルの名前と節、frontmatter、相対パスのリンク）に関わること、つまり形どおりに作る・形で引く・必要な深さだけ読む・形に合っているか確かめる・形を保って動かす、は CLI。中身に関わること、つまり何を書くか・何を読むか決める・外の世界（コードリポジトリ・PR）と突き合わせる・コミットする、は CLI にせずスキルに手順を書く（3 節）
- **CLI は補助ツールで、無くても成り立つ。** CLI を通さないと書けない・コミットできない、という強制はしない。人は CLI を使わない
- **決まりの正本はスキルで、スキルは必須。** 形（ディレクトリ・名前・frontmatter・節・リンク）も書き方も手順もスキルに書き、ツリーに触るエージェントは必ず読む。CLI は同じ形を実装する。ツール側で二重になるのは構わない（「1 つの事実は 1 か所」はツリーの中身の決まりで、スキル・CLI・設計文書には当てはめない）。ルートの README.md は人向けの軽い概要。設計文書はこのリポジトリの `docs/` に置く
- **ずれは手順ではなく基準で扱う。別の話が 2 つある。** 反映漏れや、放置・形骸化した不整合（PR が閉じているのに `inprogress`、など）は直すべきもので、しきい値を待たない。自分のタスクの分はそのとき直し、他のタスクの分はユーザーに伝えて確認が取れたら直す（2.1）。直近の作業がぶつかって起きた不整合は、不整合を含むコミットを入れた側が直す・相手の作業は勝手に直さない・相手側の直しは相手自身がこちらの直しの後で、の 3 つで決める（2.3）。セッションの始めや月 1 度のような定期の点検は無い
- **同時書き込みは厳密に防がず、後から直せれば十分。** 防ぐ仕組み（ロック、印、hook）は持たない。壊れにくい書き方と、壊れたときの見つけ方と直し方を持つ（2.3）
- **人も直接書く。** 人は形を守らなくてもよく、コミットもしなくてよい。人とエージェントがぶつかる場面を別に考える（2.4）
- **守りたいのは内容の不整合で、放置ではない。** 触られていないファイルは、中身が正しければそのままでよい

| 問題 | 対策（この文書の節） |
| --- | --- |
| 作業は進んでいるのに文書が古い。アーカイブされずに残る | 進めた側がそのとき書く。見つけたずれは直すべきもので、しきい値を待たない（他のタスクの分はユーザーに確認してから）。タスクの archive への移動は `status` から決まるので `desk archive` をいつやっても同じ（2.1） |
| ディレクトリ・frontmatter・節の形が崩れる | `desk new` が形どおりに作り、`desk check` が形を確かめ、機械的な直しは `--fix` でやる（3 節） |
| 決まりがどこにあるか分からない | 正本はスキルで必須。CLI は同じ形を実装し、README は人向けの概要（1 節） |
| メンテすべきものが更新されない | 元になるものが変わったら、それを書いている文書を直す。古いだけのものは挙げない（2.2） |
| 複数のエージェントが同時に書き込んで壊れる・ずれる | 壊れにくい書き方 3 つ、気づく場所 2 つ、直すのは誰かを決める基準 3 つ（2.3） |
| 人とエージェントの作業がぶつかる | 人の書き方を縛らず、エージェント側が人の変更を読む・混ぜない・消さない（2.4） |
| ナレッジを段階的に読まない（全部 `cat` してしまう） | 概要だけ・本文・詳細までを切り出す `desk read`（と `ls`・`graph` の `--level`）。どの段まで読むかはスキルの手順（2.5） |

## 1. 役割分担

| もの | 役割 |
| --- | --- |
| このリポジトリ | 仕組み。CLI のコード（`cli/`）、スキルの本体（`skill/`）、設計文書（`docs/`）。ドキュメントのツリーとは分け、どちらもどこに置いてもよい |
| スキル `desk` | **決まりの正本（形・書き方・手順の全部）。必須。**始めに何を読み、どう確かめ、どう書き、どう直し、終わりに何をするか。本体はこのリポジトリの `skill/SKILL.md`。エージェントのスキルの場所からリンクして使う（4 節） |
| CLI `desk` | スキルと同じ形を実装した補助ツール（二重になってよい）。形どおりに作る `init`・`new`、形で引く `ls`・`graph`、必要な深さだけ読む `read`、形に合っているか確かめる `check`（`--rules` で実装している形の一覧）、リンクを付け替えながら動かす `archive`・`mv`（3 節） |
| ルートの README.md、プロジェクトの README.md | 人向けの軽い概要。何のツリー／プロジェクトか、どこに何があるか、人向けの決まり 3 行、詳しくはどこか。決まりの正本ではない。ルートのものは `desk init` が、プロジェクトのものは `desk new project` が作る |
| git | 履歴と、戻す手段。壊れたときの「何がいつ変わったか」はここで分かる。CLI はコミットしない |

## 2. 守り方

### 2.1 進んでいるのに反映されていない（アーカイブ漏れを含む）

反映漏れと、放置されて形骸化した不整合の話。直近の作業がぶつかって起きたずれ（2.3）とは別の話で、混ぜない。文書の `status` や日付を信じず、**進み具合が分かる別のもの（コードリポジトリや PR など）と突き合わせる。** 基準は 2 つで、しきい値や定期の点検は無い。

- **進めた側が、そのとき書く。** 作業を進めたセッションが、同じ区切りでタスクのファイルを直す
- **見つけたずれは直すべきもの。** 「N 日たってから」のようなしきい値は持たず、セッションの始めの定期確認にもしない。自分のタスクの分は読んだときに直す。他のタスクの分は、本来のタスクをそっちのけにして黙って直すのではなく、見つけたことをユーザーに伝え、確認が取れたら直す。その直しが他の作業とぶつかったら 2.3 の基準で直す

ツリーの中だけで分かるずれは `desk check` が挙げ、外の世界との突き合わせはエージェントがやる（3 節）。

- 触られていないだけのタスク（コードにも PR にも動きがない）はずれではない
- 人に聞くことなら `owner: human` の子タスクにする

### 2.2 変化があったのに、それを書いている文書が触られていない

「いまこうなっている」を書いている文書は、元になるものが変わったら直す。**古いだけでは挙げず、変化の起点があるものだけ挙げる。** 定期的な点検は要らない。確かめて変えなかったときは `verified` に日付を書いてよい（任意）。

### 2.3 同時に書いたとき

複数のセッションが同じツリーを書く。**厳密には防がない。** 壊れにくい書き方を 3 つ守り、壊れたら見つけて直す。git に小さく残っていれば、何がいつ変わったかは追えるので直せる。

**壊れにくい書き方（習慣であって保証ではない）。**

1. **既存のファイルは全体を書き直さず、直前に読み直して、該当箇所の置換で直す。** 置換元が変わっていれば失敗して、古い理解で上書きしたことに気づける。追記（タスクのログの節・溜めるメモ・素材）は末尾だけ
2. **`git add <パス>...` だけ使い、小さくこまめにコミットする。** `git add -A` を使わない。これで他のセッションや人の途中の変更を巻き込まない
3. **相手の作業は勝手に直さない。** 他のタスクのファイルと、相手が書いた中身は触らない

**壊れ方と直し方。** git のブランチや worktree を分けても防げるのは 1〜3 で、4 は構造と確かめでしか扱えない。

| 壊れ方 | 例 | どう気づくか | 直し方 |
| --- | --- | --- | --- |
| 1 ファイルの破壊 | 2 つのセッションが同じファイルを読んで書き、後の書き込みが前の変更を消す | `git diff` に「自分が書いていないのに消えた行」がある。置換が失敗する | `git log -p <ファイル>` で消えた変更を見て戻す。置換で書いていれば起きにくい |
| 2 git の操作 | `git add -A` が途中の変更を巻き込む。同時の `commit` | コミットに自分のタスク以外のファイルが入っている | `git reset HEAD~ --soft` で分け直す。習慣 2 で起きにくい |
| 3 テキストの衝突 | ブランチを分けた場合のマージ衝突 | git が止める | 1 本のワーキングツリーなので起きない（design.md 9 節） |
| 4 内容の不整合（テキストは衝突しない） | archive に移した後に古いパスへ追記して同じ名前のファイルが 2 つになる。相手が動かしたファイルへの古いパスのリンクを書く。`wiki/` の値を直した直後に古い値を前提の文書を書く。「いま」を古い理解で書き直す。同じ日に同じ slug で作る | 書く直前の読み直しと、コミット直後の `git log`（下の「気づく場所」）。手元で確かめたければ `desk check` | 重複したファイルは中身を 1 つに寄せて片方を消す。古い値を前提にした文書は読み直して書き直す |

**構造で面積を減らす**（design.md の決まりそのもの）。1 つの事実は 1 か所、状態はタスクのファイルの 1 節にだけ、記録は追記だけ、識別はパスで名前は種類の中で一意、導出できるものは書かない。これがあるので、4 が起きても直す場所は 1 つで済む。

直近の作業がぶつかって起きたずれの話。放置・形骸化した不整合（2.1）とは別で、混ぜない。**気づく場所は 2 つ、直すのは誰かを決める基準は 3 つ。** 手順を増やさず、これで判断する。

気づく場所:

- **書く直前。** 読み直して置換で書く（習慣 1）。同じ箇所を相手が先に書いていれば置換が失敗し、別の箇所なら読み直したときに相手の変更が目に入る
- **コミットした直後。** `git log --since=<セッションの始め> --format='%h %s' -- <自分が触ったファイル>` を見る。自分のタスク以外のコミットが混ざっていたら、その差分を読んで自分の変更とずれていないか見る。あわせて `git show --stat HEAD` で、自分のコミットに自分が書いていない変更（相手の途中の変更）が入っていないか見る

機械で見つかるのは構造のずれまで。「いま」を古い理解で書き直した、`wiki/` の値と別の文書の前提がずれた、といった意味のずれは、次にそれを読むエージェントが気づく。だから 1 つの事実は 1 か所にして、読む場所と直す場所を 1 つにしている。

直すのは誰か:

1. **直すのは、不整合を含むコミットを入れた側。** 順番ではなく、どのコミットに入ったかで決まる。たいていは後からコミットした側（コミット直後の確認で相手のコミットが見えるのはその側）。ただし 1 本のワーキングツリーでは、先に `git add <パス>` した側が相手の途中の変更まで同じコミットに入れてしまうことがあり（後の側はコミットするものが無いか失敗する）、そのときは先にコミットした側。どちらでも直す責任は 1 つに決まる
2. **相手の作業は勝手に直さない。** 直すのは自分の側（自分のタスクのファイル、自分が書いた中身）だけ。相手のタスクのファイルや相手が書いた中身を直す必要があれば、ユーザーに伝える（相手のエージェントに伝える手段があるとは限らない。自分のタスクのログにも 1 行残す）。ユーザーの確認が取れたら直してよく、その直しがまた衝突したら同じ基準で直す
3. **相手側にも直しが要るなら、相手自身が、こちらの直しが済んでから対応する。** こちらは自分の直しを先にコミットして待つだけ。相手は次に書くかコミットしたとき（気づく場所と同じ）にこちらの直しを見て、自分の側を直す

### 2.4 人が直接書くとき

人はエディタで直接書く。形を守らなくてよく、コミットもしなくてよい。**合わせるのはエージェント側。**

| 場面 | 起きること | エージェントの決まり |
| --- | --- | --- |
| 人がファイルを書いて、コミットしていない | 作業ツリーが HEAD より新しい | 読むのは作業ツリー（いつもどおり）。人の未コミットの変更は人のもので、自分の変更と混ぜない（習慣 2）。セッションの終わりに、人の変更が残っていれば **別のコミット**（`docs(<タスク>): 人の編集を取り込む`）で入れる |
| 人がエディタで開いているファイルを、エージェントが置換で直す | エディタは変更されていないバッファなら読み直す。変更中のバッファなら保存時に上書きの確認が出る | 人が最近触ったファイル（`git status` で未コミット、か直近のコミットが人の編集の取り込み）は、できるだけ書かない。書いたら「いま」か報告で伝える |
| 人が保存して、エージェントの変更を消す | エディタは全体を書くので、古いバッファの保存はエージェントの直近の変更を消す | エージェントは書いたらすぐコミットしておく（習慣 2）。そのファイルに書く前の読み直しで `git diff -- <ファイル>` を見て、**人の未コミットの変更に、直近のコミットで足した内容の削除が含まれていたら、意図した削除か人に聞く**（`owner: human` の子タスクか、直接） |
| 人が形を守らずに書く（frontmatter が無い、名前に日付が無い、リンクが絶対パスや `~` 始まり、ファイルを Finder で動かしてリンクが切れた） | `desk ls` や `desk graph` から漏れる。`desk check` が挙げる | 見つけたエージェントが整える。足りない frontmatter のキーは `desk check --fix` が空で足し、値は手で書く。切れたリンクは、同じ名前のファイルがツリーに 1 つだけあれば `--fix` が付け替え、それ以外と名前は手で直す。文面は人の言葉を書き換えない（`inbox/` と同じ） |
| 人がどこに書けばいいか迷う | 決まりが多すぎる | 人向けの決まりは README に 3 行だけ: どこに書いてもよい、迷ったら `inbox/`、コミットはしなくてよい |

- エージェントが主に書く場所に人が書いても構わない。形がずれていたら `desk check` が挙げるので、エージェントが整える

### 2.5 ナレッジと原則を段階的に読ませる

design.md 6 節の段 0・1・2 を、名前だけで、必要な深さだけ読める形にする。**切り出しは CLI、何をどの段まで読むかはスキル。** 素の操作だと「概要だけ」が切り出しにくい（`description` は複数行の YAML でもよく `grep '^description:'` では切れる、`head` は節の途中で切れる、「いま」の 1 行目や特定の節だけを取るには毎回 awk を書く）ので、エージェントは結局 `cat` で全部読んでしまう。ここは CLI に持たせる。

| 段 | 何を読むか | CLI | いつ |
| --- | --- | --- | --- |
| 0 | ルートと作業中のプロジェクトの、原則の本文と、全ナレッジの名前と `description` | `desk ls principle --project <p> --level 1`、`desk ls knowledge --project <p> --level 0` | セッションの始め（必ず） |
| 1 | ナレッジの本文 | `desk read <パス>` | `description` が作業に当てはまるとき。作業の種類が変わったとき |
| 2 | 詳細（本文が指すファイル） | `desk read <パス> --level 2` | 段 1 が指していて、要るとき |
| 長い文書 | 見出しだけ → 要る節だけ | `desk read <パス> --outline`、`desk read <パス> --section <見出し>,...` | 全部は要らないとき |

- 段 0 の出力は 1 件 1〜3 行（名前、種類、`description`。タスクなら `status` と「いま」の 1 行目も）。ナレッジが 100 件あっても始めに読むのは数百行で済む
- `desk graph <パス>` は隣接（指す原則、詳細、根拠、指されているもの）を段 0 で出すので、次に何を読むかをそこで決める。読むと決めたら `desk read`
- スキルの決まり: 作業の種類が変わったら段 0 を見直して段 1 を読む。ナレッジに従わなかったときは理由をタスクのログに残す。ナレッジが古ければ直すか、`materials/` に 1 件書く
- CLI が無いときの代わりは `cat`（全部読む）と `grep -H '^description:'`（1 行の `description` だけ拾える）。読めなくはないが段 0 が成り立たないので、ここは CLI に持たせている

## 3. CLI `desk`

### 目的

CLI の目的は 1 つ。**ツリーの「形」を、人とエージェントが毎回読んで手で守らなくても済むようにする。** 形とは、ディレクトリの構成、ファイルの名前と節、frontmatter のキーと値、相対パスのリンク、`assets/`、git の最終更新。形を扱う操作は 5 つで、コマンドはそれに対応する。

| 形を… | コマンド | 素の操作でやると |
| --- | --- | --- |
| 作る | `init`（ルート）、`new`（プロジェクト・タスク・各種ファイル） | 形を見ながら手で書く。雛形が無いので節やキーが抜ける |
| 引く | `ls`（frontmatter と git で絞る）、`graph`（リンクのグラフをたどる） | YAML の配列や何段ものリンクで、毎回スクリプトを書く |
| 読む | `read`（概要だけ・見出しだけ・節だけ・本文・詳細まで） | 「概要だけ」が切り出せず `cat` で全部読む（2.5） |
| 確かめる | `check`（形に合っているか。ツリーの中だけで分かるずれ。機械的な直しは `--fix`） | 決まりを全部覚えて 1 ファイルずつ見る。見落とす |
| 動かす | `archive`（まとめて同じ形で `archive/` へ。タスクには `status` を書く）、`mv`（任意の移動）。どちらもリンクを付け替える | `git mv` のたびに `grep -rl` で古いパスを探して直す。漏れてリンクが切れる |

形の定義（種類ごとの置き場所、名前の形、frontmatter のキーと値、必須の節、予約名）の正本はスキルで、CLI は同じものを実装する（二重になってよい）。`desk check --rules` は CLI が実装している形の一覧で、スキルと食い違えばスキルが正しく、CLI を直す。

CLI にしないもの: 中身を書く、何を読むか決める（組み立て）、外の世界（コードリポジトリ・PR・worktree）と突き合わせる、コミット、ロックや hook や「CLI を通さないと書けない」仕組み。CLI は補助ツールで、無くても形の一覧とスキルを読めば手でできる（「概要だけ読む」だけは `cat` で全部読むことになる）。2.1〜2.5 の確かめ方と読み方は、全部このコマンドの上に書ける。

### 前提

- Go の単一バイナリ。外部依存は `git` だけ
- ルートは置き場所を決めない。印のファイル `.desk` があるディレクトリがルートで、作業ディレクトリから上にたどって見つける。見つからなければ（ツリーの外で実行したら）何も書き換えずにエラーで止まり、推測して続けない。`desk root` がいまのルートを出す
- 読むたびにツリー全体を走査する（数千ファイルまでなら十分速い）。保存しない。設定ファイルも持たない
- 書く操作（`init`・`new`・`archive`・`mv`・`check --fix`）はファイルを作る・動かす・直すだけで、コミットはしない。コミットはエージェント（か人）が `git add <パス>` でやる。既にあるものは作らず、済んでいることはやらない（何度やっても同じ）
- コードはこのリポジトリの `cli/`。`go install ./cli/cmd/desk` でバイナリを入れる
- ファイルの指定はパス（作業ディレクトリから、またはルートから）。名前だけでも、プロジェクトの中で 1 件に決まれば通り、複数あれば候補を出して止まる
- 出力は人もモデルも読める表。`--json` と `--paths`（パスだけ）と `--level 0|1|2`（当たったものを `read` のその段で出す。2.5）を持つ

### `desk ls`

```
desk ls [<種類>] [--name <名前>] [--project <名前>] [--archived]
        [--where <キー><演算子><値>]... [--modified-before <日数>] [--modified-after <日数>]
        [--fields <列>,...] [--json | --paths | --level 0|1|2]
```

- 種類は `task` `artifact` `inbox` `library` `principle` `knowledge` `material` `wiki` `project`。省略すると全部。`archive/` の中は `--archived` で含める
- `--name` はファイル名で引く。同じ名前が複数のプロジェクトにあれば全部出す（`--project` で絞る）
- `--where <キー><演算子><値>`。演算子は `=` `!=` `~`（含む。配列は要素のどれか、文字列は部分一致、`~a,b` はどれか）`<` `>`（日付と数）。複数は AND。キーは frontmatter のどれでも。`[]` は空の配列
- `--modified-before`・`--modified-after`: 最終コミットの日付
- `--fields`: `name` `path` `project` `modified`、frontmatter のキー、本文から取る `title`（見出し）と `now`（「いま」の 1 行目）
- 例

  ```
  desk ls task --where status=inprogress --fields name,repo,branch,pr,modified
  desk ls task --where owner=human --where status~todo,inprogress
  desk ls task --where 'status~done,dropped'                       # archive/ の外に残っているもの
  desk ls artifact --where tasks~2026-11-09-printable-menu --level 1   # パスの部分一致
  desk ls material --where knowledge=[] --project recipe-app          # 蒸留待ち
  desk ls knowledge --where principle=prefer-structure-over-patches
  desk ls library --where tags~pagination --fields name,url,title
  ```

### `desk graph`

```
desk graph <パス> [--in | --out] [--via <キー>,...] [--depth <n> | all]
           [--format tree | paths | dot] [--level 0|1|2]
desk graph --all [--via ...] [--format dot]
```

- ノードはファイル（`assets/` の中も含む）、辺は相対パスのリンクで、frontmatter のキーが辺の種類になる（本文の中は `body`）。方向は「書いてあるファイル → 指された先」。`--in` は指されているもの、`--out` は指しているもの、省略は両方を 1 段
- 出力の各行はパス、種類、辺の種類、`description`（あれば）。`--level` を付けると各ノードを `read` のその段で出す
- 例

  ```
  desk graph recipe-app/tasks/2026-09-07-meal-planner.md --in --via parent --depth all --format tree   # 子孫の木
  desk graph 2026-11-11-print-preview.md --out --via depends_on --depth all   # 何を待っているか（名前だけ）
  desk graph 2026-10-14-meal-planner-shopping-list.md --in --via depends_on   # これを待っているもの
  desk graph principles/prefer-structure-over-patches.md --in --via principle       # この原則に紐づくナレッジ
  desk graph recipe-app/wiki/meal-planner/overview.md --in                                # この wiki を指しているもの
  desk graph 2026-11-09-printable-menu.md --in --format paths            # 閉じるとき、一緒に archive に移す候補
  desk graph --all --via parent,depends_on --format dot | dot -Tsvg             # タスクの全体図
  ```

### `desk read`

```
desk read <パス>... [--level 0 | 1 | 2] [--outline] [--section <見出し>,...]
desk read --stdin [...]            # desk ls --paths / desk graph --format paths の出力を受ける
```

- パス（か、1 件に決まる名前）で引く。省略時は `--level 1`
- `--level 0`: 概要。パス、種類、プロジェクト、`description`。タスクなら `status`・`owner`・「いま」の 1 行目も。1 件 1〜3 行
- `--level 1`: そのファイル全体（frontmatter と本文）
- `--level 2`: そのファイルと、本文がリンクで指す `.md`（1 段）。指す先はまず `--level 0` で並べ、本文は指された順に続ける
- `--outline`: 見出しと、各節の行数だけ
- `--section <見出し>,...`: その節だけ（見出しの行から、次の同じ深さの見出しの前まで）。無い見出しは注記して飛ばす
- 例

  ```
  desk read principles/prefer-structure-over-patches.md             # 段 1
  desk read knowledge/fix-by-design-not-by-patch.md --level 2       # 段 2（詳細まで）
  desk read 2026-09-07-meal-planner.md --section 目的,いま,決まり     # 親タスクの頭と決まりだけ（名前だけ）
  desk read recipe-app/wiki/meal-planner/overview.md --outline            # 長い wiki の見出しだけ
  desk ls knowledge --project recipe-app --level 0                     # 段 0（ls 側で同じこと）
  ```

### `desk init`・`desk root`

```
desk init [<パス>]        # 省略時は作業ディレクトリ
desk root                 # いまのルートの絶対パス
```

- ルートを作る: 印の `.desk`、`README.md`（人向けの概要。何のツリーか、ツリー図、人向けの決まり 3 行、詳しくはスキル `desk`）、プロジェクト `projects/misc/` の README、`.gitignore`。空のディレクトリは作らない（`principles/`・`knowledge/`・`archive/`・`assets/` は要るときに作る）。どこに置いたかはツリーにも仕組みにも書かない
- そのディレクトリが git リポジトリのいちばん上でなければ `git init` する。まだコミットが無ければ、作ったファイルで最初のコミットを作る（これだけは CLI がコミットする。空のリポジトリに履歴を作るため）。コミットがあるリポジトリではコミットせず、作ったファイルを出す
- 既にあるファイルは触らず、足りないものだけ作る。もうルート（`.desk` がある）なら何もしない。ツリーの中（上のディレクトリに `.desk` がある）には作らず、何も書き換えずにエラーで止まる（ツリーの中にツリーを作らない）
- `desk root` は、エージェントがコミットや素の操作でルートを使うとき（`git -C "$(desk root)" …`）のため

### `desk new`

```
desk new project <名前>
desk new <種類> <slug> [--project <名前>] [--parent <タスク>] [--owner human] [--title <見出し>]
```

- 種類は `task` `artifact` `inbox` `library` `principle` `knowledge` `material` `wiki`。日付が要る種類（`task` `material` `inbox` `library`）は今日の日付を付ける
- frontmatter と節の見出しを形どおりに書いたファイルを、正しい置き場所に作る。中身は書かない（中身はエージェントと人）。ディレクトリが無ければ作る（要るときに作る、の原則どおり空のディレクトリは作らない）
- 同じ種類に同じ名前が既にあれば（`archive/` の中も含めて）作らずに止まり、そのパスを出す。同じ日に同じ slug で 2 つのセッションが作ろうとしても 2 つにならない
- `project` はプロジェクトのディレクトリと README.md（人向けの概要）だけ。`task` は `status: todo` と `owner` を書き、`--parent` は相対パスにして書く。ログの節は要るときにエージェントが足す
- 作ったパスを出すので、エージェントはそのまま中身を書いて `git add <パス>` する

### `desk check`

```
desk check [--project <名前>] [--name <名前>] [--fix] [--rules] [--json]
```

- 形に合っているかと、ツリーの中だけで分かるずれを挙げる。1 行 = ファイル、何が、どう直すか。見つかれば終了コードは 1（何かを止めるためではなく、スクリプトから使えるように）
- 見るもの

  | 何を | 例 |
  | --- | --- |
  | ディレクトリ | ルートに決まった名前以外のもの、`projects/` の直下にプロジェクト以外のもの、プロジェクトに決まり以外のディレクトリ、`archive/` の中の形 |
  | ファイルの名前 | 日付が要る種類に日付が無い、同じ種類の中で名前が重複している（`archive/` の中と外に同じ名前） |
  | frontmatter | 無い、必須キーが無い、`status`・`owner` の値が決まりの外、`parent`・`depends_on`・`tasks`・`principle`・`sources` のパスが無い |
  | リンク | 本文と frontmatter のリンクの先が無い（切れたリンク）、相対パスでないリンク（絶対パス、`~` 始まり、名前だけ）、`assets/` の中にどこからも指されていないファイル |
  | 内容の構成 | タスクに必須の節（目的・いま・成果物・現在地・決まり・手順。`owner: human` は目的・成果物）が無い、ログの節が最後にない、ナレッジに `description` か `principle` が無い（ほかのナレッジの本文から指されている詳細には `principle` を求めない） |
  | ツリーの中のずれ | `done`・`dropped` のタスクが `archive/` の外（逆も）。`depends_on` に `done` でないものがあるのに `inprogress`・`done`、`todo` が `backlog` に依存、`dropped` 以外が `dropped` に依存。子が `inprogress` なのに親が `backlog`・`todo`、子が `todo` なのに親が `backlog`、親が終わっているのに子が終わっていない、子が全部終わっているのに親が `inprogress`。`parent`・`depends_on` が自分自身を指す、循環している |

- 見ないもの: 中身の正しさ。外の世界との食い違い（ブランチのコミット、PR の状態、worktree の実在。2.1 でエージェントが見る）。「触られていない」（守るのは不整合であって放置ではない）
- `--fix` は機械的に 1 通りに決まる直しだけ: 足りない frontmatter のキーを空で足す（`status`・`owner` も値は埋めない）、`status` と置き場所のずれを `archive` で直す、切れたリンクを同じ名前のファイルがツリーに 1 つだけあればそこへ付け替える（人が動かした後）。中身には触らない。関連の文書の置き場所（タスクが `archive/` にあるのに `artifacts/` が外、など）は決まりではないので挙げない。直したファイルを出すので、エージェントがその変更だけをコミットする
- `--rules` は CLI が実装している形（種類ごとの置き場所、名前の形、frontmatter のキーと値、必須の節、予約名）を人が読める形で出す。正本はスキル（1 節）
- 定期的には回さない

### `desk archive`・`desk mv`

```
desk archive <パス>... [--status done | dropped] [--dry-run]
desk archive --project <名前>
desk mv <元>... <先のディレクトリ> [--dry-run]
```

- `archive` は指定したファイルをまとめて、同じ形で `archive/` に `git mv` する（`tasks/x.md` → `archive/tasks/x.md`、`artifacts/assets/a.png` → `archive/artifacts/assets/a.png`）。タスクを指定したら `status` を書く。それ以外（`artifacts/` とその `assets/`）は自動では動かさず、一緒に移すものをエージェントが選んで並べる（候補は `desk graph <タスク> --in --format paths`。design.md 8 節）
- **動かしたあと、リンクを付け替える**: 動かしたファイルの中の相対パスと、ツリー中で動かしたファイルを指している相対パス（本文と frontmatter）。まとめて動かすので付け替えは 1 回。`--dry-run` は何を動かし、どのファイルのどの行を書き換えるかだけ出す
- 既に `archive/` にあるものは飛ばす。戻すのは `desk mv`（同じ操作の逆）
- `--project` はプロジェクトごと `projects/<p>/` から `archive/projects/<p>/` へ（中同士のリンクは深さが同じなのでそのまま。中から外を指すリンクと、外から指しているリンクを付け替える）
- `mv` は `archive/` 以外への移動と名前の変更（ナレッジをルートへ、archive から戻す）。先が決まりの外の場所なら止まる
- コミットはしない。エージェントがその変更だけを先にコミットする（design.md 9 節）

## 4. スキル `desk`

- 本体はこのリポジトリの `skill/SKILL.md`。エージェントのスキルの場所（Claude Code なら `~/.claude/skills/desk`）からシンボリックリンクで指し、スキルの変更も設計と同じリポジトリの履歴に残す
- 読むのは、ツリーに触るエージェント。誰が読んで誰に伝えるかは決めない
- **決まりの正本はこのスキルで、ツリーに触るエージェントは必ず読む。**形（種類ごとの置き場所、名前、frontmatter、必須の節）も書き方も手順もここに書く。CLI は同じ形を実装した補助で、あれば使い、無ければ素の操作でやる。README は人向けの概要なので決まりの根拠にしない

中身の構成:

1. **いつ使う。** 作業を始めるとき、タスクの状態を聞かれたとき、作業用の md を作りたくなったとき、指摘されたときややり直したとき（その場で素材を書くため）。ルートの見つけ方（ツリーの中で `desk root`）、仕組みの設計はこのスキルと同じリポジトリの `docs/`
2. **形。** 種類ごとの置き場所、名前の形、frontmatter のキーと値、必須の節、予約名、リンクの書き方（相対パス）、`assets/`（design.md 3〜8 節の形をそのまま）。`desk new` と `desk check` は同じ形を実装する。README には書かない
3. **セッションの始めに読むもの。** design.md 9 節の順。プロジェクトの README（何のプロジェクトか。短い）→ 原則の本文とナレッジの段 0（`desk ls principle --level 1`、`desk ls knowledge --level 0`。ルートと作業中のプロジェクト）→ タスク（親は `desk read <親> --section 目的,いま,決まり`）→ `artifacts/` と関係する `wiki/` の段 0。全部 `cat` しない（2.5）
4. **セッションの始めに見ること。** `git status`（人の未コミットの変更があるか。2.4）だけ。定期の点検はしない
5. **書くときの決まり。** 2.3 の習慣 3 つと、気づく場所 2 つ、直すのは誰かの基準 3 つ。人が触っているかもしれないファイルは慎重に（2.4）。新しいファイルは `desk new` で作る（無ければこのスキルの形で手で）。形がずれたファイルは `desk check --fix` で整え、残りは手で
6. **進行中。** 人にとって意味のある変化があれば「いま」を直す。人に聞くこと・人の作業は `owner: human` の子タスク。作業の種類が変わったら段 0 を見直して段 1 を読む（2.5）
7. **タスクを閉じるとき。** 子が全部終わっているか → 一緒に移す文書を選び（`desk graph <タスク> --in --format paths`）`desk archive <タスク> <文書>...` でまとめて archive へ → その変更だけを先にコミット
8. **セッションの終わり。** design.md 9 節の手順。自分の変更を `git add <パス>...` でコミットし、`git log --since=<セッションの始め> --format='%h %s' -- <触ったファイル>` に自分のタスク以外のコミットが混ざっていないか見て、ずれていれば 2.3 の基準で直す。人の未コミットの変更が残っていれば別のコミットで取り込む
9. **やらないこと。** `git add -A`、既存ファイルの全体の書き直し、一覧を手で書く、決まりをツリーの中（README など）に複製する、コードリポジトリに作業用の md を作る、人の未コミットの変更を自分のコミットに混ぜる、エージェントの決まりや形を README に書く（人向けの 3 行以外）
