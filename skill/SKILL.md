# desk

作業ドキュメントを 1 つのツリー（desk）で管理する。いちばん上（ルート）に印のファイル `.desk` がある。

- **desk はツリーの中で実行する。** ルートは、作業ディレクトリから上にたどって `.desk` のあるディレクトリ。`desk root` が出す。ツリーの外では何もせずにエラーで止まる
- git はルートで操作する（`git -C "$(desk root)" …`）
- このスキルに書くパスは、ことわりがなければルートからのパス

## このスキルについて

- **ツリーの決まりの正本はこのスキル。** ツリーに触るエージェントは必ず全部読む。形（置き場所・名前・frontmatter・節・リンク）も、書き方も、手順もここにある
- **CLI `desk` は、同じ形を実装した補助ツール。** あれば使い、無ければこのスキルの形で手でやる。`desk rules` は CLI が実装している形の一覧で、このスキルと食い違えばこのスキルが正しい
- **README.md（ルートとプロジェクト）は概要。** 決まりの根拠にしない
- **決まりの理由は `docs/` にある。** このスキルと同じリポジトリの `tree.md`・`operation.md`・`cli.md`。書いていないケースに出会ったら、1 節の原則に戻って判断する

## 1. 原則

1. **プロジェクトはみな同じ形。ルートには全プロジェクトに適用するものだけを置く。** タスクとその文書は必ずどれかのプロジェクトにある。どのプロジェクトにも属さないものは `projects/misc/` に置く
2. **ディレクトリは種類で分け、中はフラットに並べ、関係はリンクで表す。** 入れ子はプロジェクトの中で `<種類>/<ファイル>.md` の 2 段まで（例外は `wiki/` と `assets/`）。親子・依存・「どのタスクの文書か」は、frontmatter と本文の相対パスのリンクで表す
3. **1 つの事実は 1 か所に書く。** 他の場所からはリンクで指す。どこに何を書くかは 7 節が正本
4. **人に読ませるものは、簡潔に分かりやすく書く。** README、タスクの目的・いま・成果物、成果物の文書は、結論から短く
5. **時制を混ぜない。** 状態（いまどうか。上書きする）、記録（何があったか。追記だけする）、知識（次も使えること。磨いて書き直す）の 3 つを、このスキルでは「時制」と呼ぶ。時制の違うものは別のファイルに書く。例外はタスクのファイルだけで、状態の節の下に記録の節（ログ）を 1 つ持つ
6. **ファイルは要るときに作り、中身のない節や文書は置かない。** 雛形のディレクトリは無い。形はこのスキルにあり、`desk new` が形どおりに作る
7. **工程を状態にしない。** 調査中・設計中・レビュー待ちのような工程は、状態の語彙にしない
8. **git と名前で分かることは書かない。** 作成日はファイル名に、変更の時系列と古い版は git にある

## 2. ツリーの形

### 全体

```
<ルート>/
├── .desk              # ルートの印
├── README.md          # 概要（何のツリーか、どこに何があるか、人が書くときの決まり 3 行）
├── principles/        # 全プロジェクトに通じる原則
├── knowledge/         # 全プロジェクトで AI が使う知識
├── assets/            # README の画像など（要るときに）
├── archive/
│   └── projects/      # 終わったプロジェクト（中は projects/ と同じ形）
└── projects/
    ├── misc/          # どのプロジェクトにも属さないものを置く、なんでもありのプロジェクト
    └── <project>/     # 長く続く文脈（プロダクト・リポジトリ・領域）
        ├── README.md      # 何のプロジェクトか（概要）
        ├── tasks/         # タスク。1 タスク 1 ファイル
        ├── artifacts/     # タスクの文書（タスクと一緒に役目を終える）
        │   └── assets/    # 画像などの静的ファイル
        ├── wiki/          # プロジェクトの成果物としてメンテする文書。構成はプロジェクトで設計する（assets/ も置ける）
        ├── inbox/         # まだどこにも属さない未整理のものの受け箱。棚卸しして空にする
        ├── library/       # あとで参照したい情報の控え。書いた時点のまま残す
        ├── principles/    # このプロジェクトだけの原則
        ├── knowledge/     # このプロジェクトだけで AI が使う知識
        ├── materials/     # ナレッジの素材。1 件 1 ファイル
        ├── assets/        # README の画像など（要るときに）
        └── archive/       # 終わったタスクのもの。中は同じ形（archive/tasks/・archive/artifacts/・archive/artifacts/assets/）
```

- **ルートに置くのは決まった名前だけ**: `.desk`・`README.md`・`principles/`・`knowledge/`・`assets/`・`archive/`・`projects/`。ほかのファイルやディレクトリは置かない
- **プロジェクトは `projects/` の下に平らに並べ、入れ子にしない。** `projects/` の直下はプロジェクトのディレクトリだけ。プロジェクトの直下に置くファイルは README.md だけで、ディレクトリは中身があるものだけ置く。プロジェクトの名前は英小文字・数字・ハイフン
- **`.` で始まる名前はツリーの形の外。** `.desk`・`.git`・`.gitignore`・`.DS_Store` など

### ファイルの名前

- `<slug>.md`。タスク・素材・inbox・library は作った日を頭に付けて `YYYY-MM-DD-<slug>.md`
- slug は英小文字・数字・ハイフンで、中身で付ける
- 識別はパス。名前は同じ種類の中（そのプロジェクトの `archive/` の同じ種類も含めて）で一意にする

### リンク

- 本文も frontmatter も、そのファイルの場所を基準にした相対パスで書く。本文は `[文字](../artifacts/print-layout.md)`、frontmatter は同じ相対パスの文字列（同じディレクトリならファイル名だけ。それも相対パス）
- 絶対パス、`~` 始まり、`[[名前]]` は書かない。一般的なビューワーやエディタでそのまま開けるようにするため
- ログに書いた決定を指すときは、そのタスクのファイルへのパス（`../tasks/<タスク>.md`）で指す
- frontmatter でリンクとして読むキー: `parent`・`depends_on`・`tasks`・`about`・`principle`・`sources`・`source`（素材のもの。library の `source` は自由な文）・`knowledge`（素材のもの）

### 静的ファイル

- 画像などは、それを指す文書と同じディレクトリの `assets/` に置く（`artifacts/assets/`・`wiki/assets/`。README のものはプロジェクト直下やルートの `assets/`）
- 中はフラット。文書からは `![](assets/print-sample.png)` で指す
- どこからも指されていないものは消す

## 3. タスク（`tasks/`）

### タスクと手順

終わりの条件があって、ブランチ・PR・別のセッション・人への依頼のどれかを持つものがタスク。小さくても 1 タスク 1 ファイルにし、複数のタスクをまとめて書くファイルは置かない。

そのタスクの中で順にやるだけのことは**手順**で、タスクのファイルの中にチェックボックスの行で書く。手順がタスクの条件を満たすようになったら子タスクに切り出し、行を `→ [子の見出し](<子のファイル>.md)` に置き換える。

### ファイルの形

```markdown
---
status: inprogress        # 必須。backlog / todo / inprogress / done / dropped
needs_human: false        # 必須。false / true
parent: 2026-09-07-meal-planner.md                          # 親タスク（相対パス）
depends_on: [2026-10-14-meal-planner-shopping-list.md]   # 待っているタスク（相対パス）
repo: ~/src/recipe-app
branch: feature/meal-planner/printable-menu   # base: feature/meal-planner/all
worktree: ~/src/recipe-app-worktrees/meal-planner
pr: https://github.com/example/recipe-app/pull/128
---

# 献立を印刷できるようにする

## 目的
3 行まで。終わりの条件を含む。

## いま
人が知るべき粒度で 3 行まで。人にとって意味のある変化のときだけ書き換える。

## 成果物
- PR: #128, #129
- [印刷のレイアウト](../artifacts/print-layout.md)

## 現在地
次の一手と、何を待っているか。セッションごとに上書きする。

## 決まり
このタスクの中だけの運用（ブランチの切り方、確かめ方など）。

## 手順
- [x] 献立を印刷用の形に並べる
- → [印刷のプレビューを出す](2026-11-11-print-preview.md)
- → [用紙の大きさを決める](2026-11-10-decide-paper-size.md)

## ログ
### 2026-11-10
- 決定: 印刷用のページは画面と別に作る。理由: 画面をそのまま印刷すると、ボタンやメニューまで出る
- 試してやめた: 画面に印刷用のスタイルを当てるだけにする。1 週間分が 1 枚に収まらなかった
```

**節。** `needs_human: false` のタスクは、目的・いま・成果物・現在地・決まり・手順 の 6 節を持つ。目的・いま・成果物は人が読むところで、結論から短く（原則 4）。現在地・決まり・手順は状態で、上書きする。いちばん下のログは記録（下の「ログ」）。成果物の節は、PR と、成果物の文書へのリンク。数行で済む本当に軽い中身（確認の結果など）だけは、ファイルを作らずに直接書いてよい。

**frontmatter。**

- `status` と `needs_human` は必須
- `status` は `backlog`（やるか決めていない・いつか）、`todo`（やると決めた・未着手）、`inprogress`（着手している）、`done`、`dropped`。待っていることは `status` ではなく `depends_on` で表す
- `needs_human` は、人の判断か作業が要るかどうか。誰がやるかではない
- `parent`・`depends_on` は、タスクのファイルへの相対パス（同じ `tasks/` の中ならファイル名だけ）
- `repo`・`worktree` は `~` からのパス。コードリポジトリはツリーの外にあるので、相対パスにしない
- ブランチ・base・worktree・PR は、タスクが 1 本の枝を持つときに書く。複数の枝を持つなら、子タスクに分けるか、手順の行の末尾に書く。ブランチなどの正本はタスクのファイルだけで、ほかには書かない

**親子と依存。**

- 親子は、子の `parent` だけで表す。親のファイルに子を列挙しない。順序や依存を見せたいときだけ、親の手順に `→ [子](<子のファイル>.md)` の行を置く（チェックボックスは付けず、状態は子だけが持つ）
- 依存は、待つ側（後のタスク）の `depends_on` にだけ書く。逆向き（これを待っているもの）は `desk graph <タスク> --in --via depends_on` で引く
- 親子（`parent` をたどってつながる祖先と子孫）の間には、どちらの向きにも依存を張らない。依存は着手できるかを表し、親子は抽象度が違うだけの包含関係なので。子の判断を待っている親も `inprogress` のまま
- ほかの依存から導ける依存は書かない。祖先の依存は子孫にも効き、依存は推移し（A→B→C なら A→C）、依存先の子孫にも依存している（親が終わるのは子孫が全部終わったとき）。子孫で書くのは、子孫どうしの依存と、特定の子だけが外の別のタスクを待つとき

### ログ

タスクのファイルのいちばん下に「ログ」の節を置き、そのタスクの決定と経緯を、日付の小見出し（`### YYYY-MM-DD`）で追記だけする。節は要るときに作る。別のファイルにはせず、1 セッション 1 ファイルの作業ログも作らない。

- 書くのは、決定（`決定:` で始め、理由と却下した案を添える）と、残す価値のある出来事
- 書かないのは、やったことの羅列（git にある）、次の一手（現在地に書く）、人に聞くこと（人が要るタスクにする）
- 長くなってきたら、タスクが大きすぎる印なので、子タスクに分ける

### 人が要るタスク（`needs_human: true`）

人に判断してほしいこと（確認）も、人がやる作業も、`needs_human: true` のタスクに切り出す。節は 目的・成果物 の 2 つ。つなぎ方は、そのときに合うものを選ぶ。

- 切り出した元のタスクの子にする。その続きの作業も子に分けて、人が要るタスクに `depends_on` を張ってもよい
- 親子にせず、待つ側の `depends_on` で指す

```markdown
---
status: todo
needs_human: true
parent: 2026-11-09-printable-menu.md
---

# 用紙の大きさを決める

## 目的
a A4 だけ / b A4 と B5 / c 使う人が選ぶ。おすすめ a（家庭のプリンターはほとんど A4）。

## 成果物
- 決定: [献立を印刷できるようにする](2026-11-09-printable-menu.md) のログ
```

- 目的に、聞きたいことと選択肢とおすすめを書く
- 終わったら、決定や結果は切り出した元のタスクのログに書き、人が要るタスクの成果物からそれを指して `done` にする

## 4. タスクの文書（`artifacts/`）

タスクのための文書。設計、調査の結果、レビューの結果など。どれも使い捨てで、タスクが終われば `archive/` に移す。

```yaml
---
tasks: [../tasks/2026-11-09-printable-menu.md]   # 必須。どのタスクのための文書か（複数でもよい）
---
```

- 整理して書く。結論から書き、新しく分かったら最初からそうだったように書き直す
- 成果物は、タスクの「成果物」から指す

## 5. タスクを離れて残るもの

### 永続の文書（`wiki/`）

仕組みの説明、仕様、用語など、プロジェクトの成果物としてメンテし続ける文書。コードリポジトリの中の docs と同じ扱いで、プロジェクトごとに構成を設計して使う。タスクには属さない。置き場所に困ったものを置く場所ではない。

```yaml
---
description: 献立プランナーの仕組み全体。レシピ API との境目を触るときに読む   # 必須。何が書いてあるか、いつ読むか
verified: 2026-11-12        # 任意。確かめたが変えなかった日
---
```

- 入れ子にしてよい
- 特定のタスクの話は、そのタスクが終わっても残すもの（保守に要るなど）だけ置く
- メンテし続けられる量だけ持つ。古いだけの文書は問題にしない（中身が正しければそのまま）。メンテされなくなったら消す
- 近いものとの違い: `artifacts/` はタスクのための文書（使い捨て。大きなタスクの進め方も、そのタスクの文書）。`knowledge/` は AI が作業で使う決まり・手順・事実（特定のタスクに限らない開発の流れや運用も）。`wiki/` はプロジェクトそのものの「いまこうなっている」の説明

### 受け箱（`inbox/`）

まだどこにも属さない未整理のものの受け箱。出たらその場で置き、あとで棚卸しして空にする。

```markdown
---
about: ../tasks/2026-09-07-meal-planner.md     # 任意。関係するタスクや文書が分かれば
---

# iOS でレシピ一覧が遅い気がする

スクロールのとき。再現条件は未確認。先週のリリース後から？
```

- 1 件 1 ファイル、`inbox/YYYY-MM-DD-<slug>.md`
- frontmatter は `about` だけで、それも任意。必須は見出し（か本文）だけ。分からない項目は書かず、推測で埋めない
- AI が書くときは、人の言葉を言い換えない
- 状態の項目は持たない。`inbox/` にあること自体が未整理の印
- **棚卸し**は、AI が 1 件ずつ行き先の候補を出し、人が決める

  | 中身 | 行き先 |
  | --- | --- |
  | やりたいこと、やるべきこと | `tasks/` のタスク |
  | あるタスクに関する情報 | そのタスクの `artifacts/` |
  | 作業で使う決まり・手順・事実 | `knowledge/` |
  | 指摘や、やり直しの気づき | `materials/` |
  | あとで参照したい情報 | `library/` |
  | 思い出せない、もう要らない | 消す |
  | まだ決められない | そのまま残す |

### 書庫（`library/`）

あとで参照したい情報の控え。外の資料も、調べたり試したりして分かったことも、出たらその場で置く。書いた時点のもので、メンテしない。AI が要約とタグを付けて整理する。

```markdown
---
url: https://example.com/infinite-scroll-pitfalls   # あれば
source: 2026-11-10 の勉強会で聞いた話      # URL がないときの出どころ。自由な文（リンクではない）
tags: [pagination, frontend]
about: ../tasks/2026-11-09-printable-menu.md   # きっかけになったタスク。あれば
---

# 無限スクロールでハマりやすいところ

## 要約
（AI が書く。3〜5 行）

## 内容
（控えの本文。人の言葉は原文のまま）

## メモ
（人の一言があれば、そのまま）
```

- 1 件 1 ファイル、`library/YYYY-MM-DD-<slug>.md`。frontmatter は全部任意で、必須は見出しだけ。「内容」「メモ」は中身があるときだけ置く
- 不完全でも置き、あとで分かったら足す
- 人の言葉は原文のまま残す
- `archive/` には移さない
- 読んで分かったことを作業の決まりにしたくなったら、ナレッジを足して `sources` でここを指す
- 近いものとの違い: タスクの中だけで使うものは `artifacts/`、作業の決まり（原則の当てはめ）は `knowledge/`、メンテし続ける成果物は `wiki/`。`library/` は、タスクを離れてもあとで参照したい事実を、書いた時点のまま残す

## 6. 原則・ナレッジ・素材

判断のよりどころは 3 層。**原則**（抽象的で根源的な考え方）← **ナレッジ**（原則をスコープに当てはめた決まり・手順・事実）← **素材**（ナレッジになる前の出来事）。下の層は上の層を相対パスで指す。

原則とナレッジは**置き場所でスコープが決まる**。ルートのものは全プロジェクト、プロジェクトのディレクトリのものはそのプロジェクトだけに効く。ぶつかったらプロジェクトのものが勝つ。

| | 置き場所 | 1 件 | 読むとき | 時制 |
| --- | --- | --- | --- | --- |
| 原則 `principles/` | ルートとプロジェクト | `<slug>.md` | セッションの始めに本文を全部 | 知識 |
| ナレッジ `knowledge/` | ルートとプロジェクト | `<slug>.md` | 始めに `description`、要るときに本文 | 知識 |
| 素材 `materials/` | プロジェクトだけ | `YYYY-MM-DD-<slug>.md` | 蒸留するときだけ | 記録 |

### 原則（`principles/`）

ナレッジにないことでも同じ判断ができるようにするための考え方。少なく、めったに変わらない。**追加と変更はユーザーに確認する。**

```yaml
---
description: 不具合は症状を個別に塞がず、起きない構造にして直す   # 必須
principle: ../../../principles/prefer-structure-over-patches.md     # プロジェクトの原則がルートの原則を具体化したものなら
---
```

- 本文は、考え方・なぜ・適用の例を短く。セッションの始めにルートと今のプロジェクトの分を全部読むので、どちらも数ファイルに収める
- プロジェクトの原則は、本人が合わせる考え方がそのプロジェクトだけ違うとき（チームが違うなど）に置く。ルートの原則と食い違うものなら、本文にどのルートの原則とどう違うかを 1 行書く

### ナレッジ（`knowledge/`）

AI が作業で使う決まり・手順・事実。1 件 1 ファイル。**追加と変更はユーザーに確認する。**

```yaml
---
description: 不具合やレビュー指摘を直すときに読む。症状を個別に塞がず、状態を入力に結び付けて「起きない形」にする   # 必須
principle: [../principles/prefer-structure-over-patches.md, ../principles/single-source-of-truth.md]     # 必須。どの原則の当てはめか（1 つ以上）
sources: [../projects/recipe-app/materials/2026-11-10-patched-each-error-screen.md, ../projects/recipe-app/tasks/2026-11-09-printable-menu.md]
verified: 2026-11-12        # 任意
---
```

- `description` は「いつ読むか」と「何が書いてあるか」を 1〜2 行で。これで読むかどうかが決まるので、いちばん丁寧に書く
- `principle` は、どの原則の当てはめかを 1 つ以上指す（1 つなら文字列、複数ならリスト。ひとつの場面に複数の原則が効くのは自然なので、1 つに絞らない）。指す先はルートの原則か、同じプロジェクトの原則。指せないなら、原則が足りないか、ナレッジの一般化が足りない
- 本文は、決まり・なぜ・例 1 つ。詳細は別のファイルにして本文から指す。詳細のファイルには `principle` を書かない（どの原則の当てはめかは親が持つ）。ディレクトリは作らない
- そのスコープで成り立つ、いちばん一般的な形で書く。固有名は入れない（根拠は `sources` が指す）
- プロジェクトで得た知識が他でも通用すると分かったら、ルートに移す（`desk mv`）

### 素材（`materials/`）

ナレッジになる前の出来事（ユーザーの指摘、レビューの指摘、やり直し、思っていたのと違ったこと）。起きたらその場で、起きたプロジェクトの `materials/` に 1 件 1 ファイルで書く。ルートには置かない。

```markdown
---
source: ../tasks/2026-11-09-printable-menu.md   # 起きた場所。ツリーにあるときだけ書く
knowledge: []            # 必須。蒸留してできた・足したナレッジ（相対パス）。空なら蒸留待ち
---

# エラー表示を画面ごとに個別に直した

## 何が起きたか
（原文の引用、状況、なぜそうなったか。必要なだけ詳しく）

## 一般化の候補
- 同じ症状が複数の場所に出たら、個別に直す前に共通の原因を探す
```

- **蒸留**はキリのいいところでやる（蒸留待ちは `desk ls material --where knowledge=[]`）。「どの原則の現れか」を考えて、ナレッジを足すか既存のナレッジの `sources` に足し、素材の `knowledge` にそのナレッジを書く
- 蒸留した素材は消さない（`sources` が指す根拠）。一般化する価値がないと決めた素材は消す。`archive/` には移さない

### 段階的に読む

全部を最初に読まない。

| 段 | 何を読むか | CLI | いつ |
| --- | --- | --- | --- |
| 0 | ルートと今のプロジェクトの、原則の本文と、全ナレッジの名前と `description` | `desk ls principle --project <p> --level 1`、`desk ls knowledge --project <p> --level 0` | セッションの始め（必ず） |
| 1 | ナレッジの本文 | `desk read <パス>` | `description` が今の作業に当てはまるとき。作業の種類が変わったとき |
| 2 | 詳細（本文が指すファイル） | `desk read <パス> --level 2` | 本文が指していて、要るとき |
| 長い文書 | 見出しだけ → 要る節だけ | `desk read <パス> --outline`、`--section <見出し>,...` | 全部は要らないとき |

- ナレッジに従わなかったときは、理由をタスクのログに残す。ナレッジが古ければ、直す（ユーザーに確認）か、`materials/` に 1 件書く

## 7. どの情報をどこに書くか

原則 3 の正本。同じことを 2 か所に書きたくなったら、ここに戻る。ここには情報と場所の対応だけを並べる。時制（原則 5）は場所ごとの節（3〜6 節）にある。

### タスクのこと

- タスクの目的と終わりの条件 → タスクの「目的」
- 人が知るべき進み具合 → タスクの「いま」
- PR と成果物の文書へのリンク。数行で済む本当に軽い中身 → タスクの「成果物」
- 人に判断してほしいこと・やってほしいこと → `needs_human: true` の子タスク
- 次の一手と、何を待っているか → タスクの「現在地」
- そのタスクの中だけの運用 → タスクの「決まり」
- 手順と進み具合 → タスクの「手順」
- ブランチ・base・worktree・PR → タスクの frontmatter か、手順の行
- タスクの親子・依存 → 子・後のタスクの frontmatter
- 決定・理由・却下した案、残す価値のある出来事 → タスクの「ログ」
- セッションでやったこと → git のコミット

### タスクの文書（`artifacts/`）

- 設計、調査の結果、レビューの結果など、タスクのための文書 → `artifacts/`
- 文書がどのタスクのものか → その文書の frontmatter `tasks`

### タスクを離れて残るもの

- プロジェクトの成果物としてメンテし続ける文書（仕組み、仕様、用語） → `wiki/`
- まだどこにも属さない未整理のもの（棚卸し前） → `inbox/`
- あとで参照したい情報の控え → `library/`

### 判断のよりどころ

- 抽象的で根源的な考え方 → ルートかプロジェクトの `principles/`
- 判断の決まり・手順・事実 → ルートかプロジェクトの `knowledge/`
- 指摘・やり直し・思っていたのと違ったこと → そのプロジェクトの `materials/`
- 永続の文書・ナレッジ・原則を、変えずに確かめた日 → その frontmatter の `verified`

### ツリーそのもの

- ツリーの決まり（形・書き方・手順） → スキル `desk`
- 何のツリー／プロジェクトか、どこに何があるか → README.md

### 書かないもの

- コードそのもの
- コミット履歴や PR の説明文の写し（URL だけ書く）
- 機密情報（認証情報、個人情報、本番データの実値）
- git と名前から分かること（日付、変更履歴）
- 中身のない節や文書

## 8. アーカイブと移動

- タスクが終わったら（`done` か `dropped`）、タスクのファイルをプロジェクトの `archive/tasks/` に移す。そのタスクの `artifacts/`（とその `assets/`）は、一緒に移すものを選んで同じ操作でまとめて指定する（候補は `desk graph <タスク> --in --format paths`）。自動では一緒に動かさない
- `desk archive <タスク> <文書>...` が、まとめて同じ形で移し、タスクに `status` を書き、リンクを付け替える。`archive/` の中はプロジェクトと同じ形で、ファイル名は変えない
- リンクの付け替えの対象は、動かしたファイルの中のリンクと、動かしたファイルを指しているツリー中のリンク（本文と frontmatter）。まとめて動かせば 1 回で済む
- 移さないもの: `wiki/`・`library/`・`principles/`・`knowledge/`・`materials/`。`inbox/` は棚卸しで空になる
- タスクの置き場所は `status` から決まる。`done`・`dropped` で `archive/` の外にあるタスクは直すべきもので、見つけたセッションが移す（他のタスクのものはユーザーに確認してから）。関連の文書の置き場所は `status` から導かない
- プロジェクトごと終わったら、`desk archive --project <名前>` で `archive/projects/<名前>/` に移す
- `archive/` 以外への移動（ナレッジをルートへ、名前の変更、archive から戻す）は `desk mv <元>... <先>`。同じくリンクを付け替える

## 9. セッションの流れ

### 始めに読むもの

全部 `cat` しない。

1. プロジェクトの README.md（何のプロジェクトか。短い）
2. ルートと今のプロジェクトの原則の本文（`desk ls principle --project <p> --level 1`）と、ナレッジの段 0（`desk ls knowledge --project <p> --level 0`）
3. タスクのファイル。親があれば親の頭と決まり（`desk read <親> --section 目的,いま,決まり`）
4. `tasks` でこのタスクを指す `artifacts/`（`desk graph <タスク> --in --via tasks`）と、`description` が関係する `wiki/`（`desk ls wiki --project <p>`）
5. 作業に合わせて、ナレッジの段 1・段 2

見るのは `git -C "$(desk root)" status`（人の未コミットの変更があるか。10 節）だけ。定期の点検はしない。

### 進めながら

- **進めた側が、そのとき書く。** 作業を進めたセッションが、同じ区切りでタスクのファイルを直す。「いま」と「成果物」は、人にとって意味のある変化のときだけ
- **人に聞くこと・人がやる作業は、人が要るタスクにする。** 人が要るタスクに切り出す（3 節）
- **指摘されたとき、やり直したときは、その場で素材を書く。** 起きたプロジェクトの `materials/` に 1 件（6 節）
- **作業の種類が変わったら、ナレッジを読み直す。** 段 0 を見直して段 1 を読む（6 節）
- **見つけたずれは直すべきもの。** しきい値（「N 日たってから」）も、定期の点検も無い。文書の `status` や日付を信じず、進み具合が分かる別のもの（コードリポジトリや PR など）と突き合わせる。自分のタスクの分は読んだときに直し、他のタスクの分はユーザーに伝えて確認が取れたら直す（10 節の「直すのは誰か」と同じ）。ツリーの中だけで分かるずれは `desk check` が挙げる
- **変化があったら、それを書いている文書を直す。** 古いだけではずれではない。触られていないだけのタスク（コードにも PR にも動きがない）はずれではない

### タスクを閉じる

1. 子が全部終わっているか見る（`desk graph <タスク> --in --via parent`）。残りがあれば手順に書くか、子を閉じる
2. 一緒に移す文書を選ぶ（`desk graph <タスク> --in --format paths`）
3. `desk archive <タスク> <文書>...` でまとめて移す
4. その変更だけを先にコミットする

### 終わりにやること

1. タスクの現在地と手順を直す
2. 決めたことと、残す価値のある出来事をタスクのログに追記する
3. 人にとって意味のある変化があったときだけ、「いま」と「成果物」を直す
4. このタスクで変わったことを書いている文書があれば直す。タスクを閉じるなら上の「タスクを閉じる」
5. `inbox/` に未整理が溜まっていたら、棚卸しを提案する
6. 自分のファイルだけを `git -C "$(desk root)" add <パス>...` して 1 コミット。メッセージは `docs(<タスクの名前>): <一言>`、本文にやったことを 1〜3 行。コミット直後に 10 節の「ずれに気づく場所」を見る
7. 人の未コミットの変更が残っていれば、別のコミット（`docs(<タスク>): 人の編集を取り込む`）で取り込む

## 10. 同時に書いても壊さないために

ツリーは 1 本のワーキングツリーで、全セッションが `main` に直接コミットする。ブランチや worktree は切らない。同時書き込みは厳密には防がず、壊れにくい書き方を守り、壊れたら git を頼りに直す。

### 壊れにくい書き方（3 つ）

1. **既存のファイルは全体を書き直さず、直前に読み直して、該当箇所の置換で直す。** 置換元が変わっていれば失敗して、古い理解で上書きしたことに気づける。追記（ログ・素材）は末尾だけ
2. **`git add <パス>...` だけ使い、小さくこまめにコミットする。** `git add -A`・`git add .`・`git commit -a` を使わない
3. **相手の作業は勝手に直さない。** 他のタスクのファイルと、相手が書いた中身は触らない。1 つのタスクを同時に書くのは 1 つのセッションだけ（並べて進める作業は子タスクに分ける）

### ずれに気づく場所（2 つ）

- **書く直前。** 読み直して置換で書く（上の 1）
- **コミットした直後。** `git log --since=<セッションの始め> --format='%h %s' -- <自分が触ったファイル>` に自分のタスク以外のコミットが混ざっていたら、その差分を読んで自分の変更とずれていないか見る。あわせて `git show --stat HEAD` で、自分のコミットに自分が書いていない変更が入っていないか見る

テキストが衝突しなくても中身はずれる（archive に移した後に古いパスへ追記する、`wiki/` の値を直した直後に古い値を前提の文書を書く、同じ日に同じ slug で作る）。名前の重複は見つけたら 1 つに寄せるか名前を変える（`desk check` が挙げる）。

### 直すのは誰か（3 つ）

1. **不整合を含むコミットを入れた側が直す。** 順番ではなく、どのコミットに入ったかで決まる
2. **相手の作業は勝手に直さない。** 直すのは自分の側だけ。相手の側に直しが要るならユーザーに伝え（自分のタスクのログにも 1 行残す）、確認が取れたら直してよい
3. **相手側にも直しが要るなら、相手自身が、こちらの直しが済んでから対応する。** こちらは自分の直しを先にコミットして待つ

### 人が直接書いたとき

人はエディタで直接書き、形を守らなくてよく、コミットもしなくてよい。合わせるのはエージェント側。

- 読むのは作業ツリー。人の未コミットの変更は、そのまま正として読む
- 人の未コミットの変更は、自分のコミットに混ぜない。セッションの終わりに残っていれば、別のコミット（`docs(<タスク>): 人の編集を取り込む`）で取り込む
- 人が最近触ったファイルは、できるだけ書かない。書いたら伝える
- 人の未コミットの変更に、直近のコミットで足した内容の削除が含まれていたら（古いバッファの保存で消えた疑い）、意図した削除か人に聞く
- 形がずれたファイルは、見つけたエージェントが整える（機械的なものは `desk check --fix`、残りは手で）。文面は人の言葉を書き換えない

### 新しいファイル

`desk new` で作る（無ければこのスキルの形で手で）。タスクの節（3 節）は、まだ書くことが無くても見出しを残す。それ以外で `desk new` が置いた節に書くことが無ければ消す。

## 11. 書き方の決まり

1. **状態と知識は「最初からそうだった」形に書き直す。** 版や変更の経緯（「〜から変更」「以前は〜だったが」など）を書かない。版の違いは git、経緯はタスクのログにある
2. **記録は追記だけ、整理は別のファイルに。** 記録は並べ替えたり書き換えたりしない。整理したくなったら別のファイルに書き起こす
3. **経緯は書きすぎない。** 決定は結論と理由を 1〜3 行。会話の引用は要点だけ。やったことの羅列は git に任せる
4. **主題が増えたらファイルを分ける。** 1 ファイル 1 主題。別の主題が育ったら別のファイルに切り出す
5. **選択肢は決まったら消す。** 検討中の選択肢の表は、決まったら結論だけを残し、却下した案はログに 1 行書く
6. **古い内容は消す。** 役目を終えたものは消す。git にある

## 12. やらないこと

- `git add -A`・`git add .`・`git commit -a`。ブランチや worktree を切る
- 既存ファイルの全体の書き直し（置換で直す）
- 一覧を手で書く（`desk ls` で出す）
- 決まりをツリーの中（README など）に複製する。エージェントの決まりや形を README に書く（人が書くときの 3 行以外）
- コードリポジトリに作業用の md を作る
- 人の未コミットの変更を自分のコミットに混ぜる。人の言葉を書き換える
- 他のタスクのファイルや相手が書いた中身を、ユーザーの確認なしに直す
- 原則とナレッジを、ユーザーの確認なしに足す・変える

## 13. CLI `desk` の早見

形を扱う補助ツール。中身を書く、何を読むか決める、外の世界（コードリポジトリ・PR）と突き合わせる、コミットする、はエージェントがやる。書く操作（`new`・`archive`・`mv`・`check --fix`）はコミットしないので、出たパスを `git -C "$(desk root)" add <パス>...` してコミットする。ファイルの指定は、作業ディレクトリかルートからのパス、または 1 件に決まる名前。

- **ルートを作る・知る**: `desk init [<パス>]`（省略は作業ディレクトリ。ツリーの中には作らない）、`desk root`
- **プロジェクトを作る**: `desk new project <名前>`
- **タスクを作る**: `desk new task <slug> --project <p>`。子は `--parent <タスク>`（プロジェクトは親から決まる）、人が要るタスクは `--needs-human`、見出しは `--title`。日付付きの slug を渡すと、その日付で作る
- **文書などを作る**: `desk new artifact <slug> --parent <タスク>`、`desk new knowledge <slug> [--project <p>]`、`desk new material <slug> --project <p>` など
- **一覧**: `desk ls task --where status=inprogress --fields name,status,now,modified`、`desk ls task --where needs_human=true --where status~todo,inprogress`、`desk ls material --where knowledge=[]`、`desk ls inbox`、`desk ls task --modified-after 2026-11-01`（最終コミットの日。日付か日数）
- **段 0**: `desk ls principle --project <p> --level 1`、`desk ls knowledge --project <p> --level 0`
- **読む**: `desk read <パス>...`（全体）、`--level 0`（概要）、`--level 2`（指す先まで）、`--outline`、`--section 目的,いま,決まり`。`desk ls ... --paths | desk read - --level 0` のように `-` で標準入力のパスを読む
- **関係をたどる**: `desk graph <パス> --in`（指されているもの）、`--out`（指しているもの）、`--via parent,depends_on,tasks,principle,sources,body`、`--depth all`、`--format tree|paths|dot`
- **形を確かめる**: `desk check`、`desk check --name <タスク>`、`desk check --fix`。CLI が実装している形の一覧は `desk rules`
- **動かす**: `desk archive <タスク> <文書>... [--status dropped] [--dry-run]`、`desk archive --project <p>`、`desk mv <元>... <先>`

`--where` の演算子は `=`・`!=`・`~`（含む。配列は要素のどれか、`~a,b` はどれか）・`<`・`>`。パスの値は名前だけでも当たる。`--project <p>` の原則とナレッジには、ルートのものも入る。`--via`・`--fields`・`--section` と `ls` の種類は、カンマ区切りでも繰り返しでも書ける。終了コードは 0 が成功、1 が失敗か `check` で見つけたとき、2 が引数の誤り（使い方は `desk <コマンド> -h`）。
